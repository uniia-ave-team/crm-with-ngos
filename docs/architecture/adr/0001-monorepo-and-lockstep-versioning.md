# 0001. Один репозиторій, одна версія на весь продукт

- **Статус:** ухвалено
- **Дата:** 2026-09-02
- **Учасники рішення:** команда бекенду, команда фронтенду, мейнтейнери

## Контекст

Продукт складається з двох застосунків на непов'язаних стеках: ASP.NET Core API
та клієнт на Ionic Angular. Їх розробляють дві команди. Типове рішення для такої
структури — окремий репозиторій на кожну частину з незалежним версіонуванням.

Проти цього — дві властивості продукту:

1. Інсталяції обслуговують адміністратори без технічної підготовки. Будь-яка
   несумісність між версіями API та клієнта, що потрапляє на інсталяцію, стає
   інцидентом підтримки, який адміністратор не здатний діагностувати.
2. API має одного споживача — вебклієнт продукту, що виходить у тому самому
   релізі. Зовнішніх систем, які покладалися б на стабільність API, немає.

Команди планують випускати релізи синхронно.

## Рішення

Обидва застосунки розміщуються в одному репозиторії. Продукт має єдиний номер
версії за SemVer; кожен реліз збирає обидва образи під одним тегом незалежно
від того, яка частина змінилася.

Застосунки мають спільні репозиторій, версію та OpenAPI-контракт. Спільного
інструментарію немає: `dotnet` не працює з `apps/web`, `npm` — з `apps/api`;
workspace або граф збірки, що охоплював би обидві частини, не використовується.

Межі відповідальності команд визначаються `CODEOWNERS` та фільтрами шляхів у
CI.

## Наслідки

Ламка зміна API виконується одним pull request'ом, який змінює ендпоінт,
специфікацію та місця виклику. `main` не буває в стані, де одна частина
несумісна з іншою.

API не потребує версіонування, періодів застарівання та прошарків сумісності.

Наскрізні тести виконуються в pull request'і на точному коміті й блокують
злиття. `git bisect` застосовний до дефектів на межі частин.

Прийняті витрати:

- Історія комітів змішує C# і TypeScript; потрібна фільтрація за каталогом.
- Номер версії змінюється, навіть якщо змінилася одна частина.
- Інструменти оркестрації монорепозиторіїв (Nx, Turborepo) не охоплюють обидва
  стеки; спільний шар — `just` з мінімальним набором команд.
- Незалежні цикли випуску частин потребуватимуть перегляду цього рішення.

## Мобільний клієнт

Ionic дозволяє зібрати вебклієнт як мобільний застосунок через Capacitor. Таке
рішення не ухвалене; його наслідки фіксуються тут, оскільки вони прямо
стосуються цього ADR.

Мобільний застосунок проходить рецензування в магазинах і оновлюється на
пристроях користувачів із затримкою. Він стає другим споживачем API з власним
циклом випуску, тобто порушує передумову 2 з розділу «Контекст». Для його
підтримки потрібна політика сумісності: щонайменше одна попередня мінорна
версія клієнта має працювати з поточним API, а ламкі зміни — проходити період
застарівання.

Це не скасовує рішення про єдиний репозиторій і версію, але змінює правила
зміни API. Ухвалення рішення про мобільний клієнт має супроводжуватися окремим
ADR з політикою сумісності.

## Розглянуті альтернативи

**Окремі репозиторії для API та клієнта, третій — для розгортання.** Єдина
перевага — незалежні цикли випуску — не використовується. Витрати: ламка зміна
API не зливається атомарно, тож `main` одного репозиторію тимчасово несумісний з
іншим; наскрізні тести не можуть блокувати pull request без узгодження пари
комітів; локальний запуск продукту потребує трьох клонів.

**Один репозиторій, незалежно версіоновані образи.** Зберігає атомарність змін,
але повертає адміністраторам потребу узгоджувати версії. Відхилено.

**Версіонування HTTP API (`/api/v1`).** Доцільне для публічного API; для
внутрішнього з єдиним споживачем у тому самому релізі — витрати без переваг.
Буде розглянуто повторно при появі другого споживача.
