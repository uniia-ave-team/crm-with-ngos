# Розробка

Робочі домовленості команди. Про участь зовнішніх учасників —
[CONTRIBUTING.md](../CONTRIBUTING.md).

## Інструменти

| Інструмент     | Версія   | Призначення                          |
| -------------- | -------- | ------------------------------------ |
| .NET SDK       | 10       | `apps/api`                           |
| Node.js        | LTS      | `apps/web`                           |
| npm            | з Node   | `apps/web`; Angular CLI              |
| Docker Desktop | актуальна | база даних, образи іншої частини      |
| just           | актуальна | команди з `justfile`                  |

Розробникові однієї частини не потрібен інструментарій іншої: `just dev-api`
і `just dev-web` беруть іншу частину як опублікований образ `:edge`.

## Структура

| Шлях                    | Команда            | Вміст                                       |
| ----------------------- | ------------------ | ------------------------------------------- |
| `apps/api`              | Бекенд             | ASP.NET Core, EF Core, міграції             |
| `apps/web`              | Фронтенд           | Ionic Angular                               |
| `packages/api-contract` | Обидві             | `openapi.json` — контракт                   |

## Гілки

`main` завжди в стані, придатному до релізу. Робочі гілки короткоживучі,
відгалужуються від `main`: `feat/contact-import`, `fix/deal-stage-order`,
`chore/bump-caddy`. Pull request'и вливаються через squash merge.

Гілки `develop` немає: при єдиній версії продукту вона створює місце для
розбіжності між частинами.

## Коміти

Формат — [Conventional Commits](https://www.conventionalcommits.org). З
повідомлень генеруються changelog і номер версії.

```
feat(api): додано імпорт контактів із CSV
fix(web): фільтр воронки зберігається після перезавантаження сторінки
feat(api)!: Deal.amount перейменовано на Deal.value
```

Позначка `!` або футер `BREAKING CHANGE:` означає зміну, яка впливає на дані
або конфігурацію встановлених інсталяцій і потребує дій адміністратора. Зміна
внутрішнього HTTP API такою не є.

## Зміна API

API споживає лише вебклієнт продукту, тому період сумісності не потрібен. Зміна
виконується одним pull request'ом:

1. Змінити ендпоінт в `apps/api`.
2. Виконати `just contract`: перегенеровується
   `packages/api-contract/openapi.json` і Angular-клієнт у
   `apps/web/src/app/api/generated`.
3. Оновити місця виклику в `apps/web`.
4. Закомітити `openapi.json`. Згенерований клієнт не комітиться.

CI перевіряє відповідність закоміченої специфікації коду. Pull request, що
змінює специфікацію, потребує рецензії обох команд.

## Міграції бази

Міграції застосовуються автоматично при запуску контейнера API на серверах, до
яких команда не має доступу. Звідси правила:

- **Лише вперед.** Down-міграції не пишуться; відкат — відновлення з резервної
  копії.
- **Спершу розширити, потім звузити.** Нова колонка додається, запис ведеться в
  обидві; стара видаляється в наступному мінорному релізі.
- **Патч-реліз не змінює схему руйнівно.**
- **Міграція має бути безпечною при одночасному запуску** кількох екземплярів
  API: виконується під advisory lock.

## Pull request'и

Розмір — придатний для рецензії за один підхід. PR має проходити перевірки своєї
частини та перевірку контракту, якщо він її змінює. В описі вказується, що
зміниться для адміністратора інсталяції після оновлення.
