# Резервні копії

## Що потрібно зберігати

Інсталяція повністю відновлюється з двох речей:

1. **Дамп бази даних** — усі дані CRM.
2. **Секрети** — `POSTGRES_PASSWORD` і `AUTH_SIGNING_KEY` з файлу `.env` або
   налаштувань панелі. Без них дамп неможливо використати.

Секрети зберігаються в менеджері паролів організації одноразово, після
встановлення. Дампи створюються автоматично й потребують регулярного копіювання
за межі сервера.

## Автоматичні копії

Сервіс `db-backup` створює дамп бази за розкладом (за замовчуванням щодня) у
томі `crm_backups`:

| Каталог          | Вміст                                              |
| ---------------- | -------------------------------------------------- |
| `daily/`         | Щоденні копії за останні 7 днів                    |
| `weekly/`        | Щотижневі за останні 4 тижні                       |
| `monthly/`       | Щомісячні за останні 6 місяців                     |
| `last/`          | Остання створена копія                              |
| `pre-update/`    | Копії, створені `update.sh` перед кожним оновленням |

Розклад і терміни зберігання налаштовуються змінними `BACKUP_SCHEDULE`,
`BACKUP_KEEP_DAYS`, `BACKUP_KEEP_WEEKS`, `BACKUP_KEEP_MONTHS`.

Формат файлів — стиснутий SQL (`.sql.gz`), придатний для відновлення командою
`psql`.

## Копія за межами сервера

Автоматичні копії лежать на тому самому диску, що й база. Вони захищають від
помилкового видалення даних і невдалого оновлення, але не від втрати сервера.

### Рівень 1. Власний комп'ютер

Двічі клацніть `deploy/windows/backup.cmd` (Windows) або
`deploy/macos/backup.command` (macOS). Файл копії з'явиться в папці
`deploy/backups`, яка відкриється автоматично. Скопіюйте його в хмарне сховище
організації або на зовнішній носій. Робіть це щонайменше раз на тиждень і
завжди — перед оновленням.

Автоматичні щоденні копії при цьому також створюються, але лишаються на диску
комп'ютера.

### Рівень 1. Dokploy

Увімкніть у кабінеті провайдера резервне копіювання або знімки сервера. Це
основний спосіб отримати зовнішню копію без роботи в терміналі: знімок містить
і базу, і автоматичні дампи.

Додатково Dokploy уміє копіювати томи сервісу в S3-сумісне сховище за розкладом
(сервіс → **Volume Backups**); це дає копію в іншого провайдера, як рекомендовано
в розділі про розміщення даних.

### Рівень 2. Portainer

Створити копію вручну: **Containers** → `crm-db-backup-1` → **Console** →
**Connect** → виконати команду `/backup.sh`. Файл лишається в томі
`crm_backups` на сервері. Для копії за межами сервера використовуйте знімки в
кабінеті провайдера або налаштуйте `rclone` за розділом нижче.

### Рівень 2 і 3. Термінал

Швидкий спосіб отримати копію в каталозі `deploy/backups/` на сервері:

```bash
./backup.sh
```

Вивантажити останню автоматичну копію:

```bash
docker compose cp db:/backups/last ./backups-last
```

Для регулярного копіювання підходить `rclone` за розкладом cron:

```bash
# приклад: щодня о 04:00 копіювати том у сховище S3 або інше, налаштоване в rclone
0 4 * * * docker run --rm -v crm_backups:/data:ro -v /root/.config/rclone:/config/rclone rclone/rclone sync /data remote:crm-backups
```

Копію файлу `.env` зберігайте окремо від дампів.

## Копія вручну

```bash
docker compose exec -T db sh -c \
  'pg_dump -U crm -d crm --clean --if-exists | gzip -1 > /backups/manual-$(date +%Y%m%d-%H%M%S).sql.gz'
```

## Відновлення

### У ту саму інсталяцію

Зупиніть API, щоб під час відновлення не було запису в базу, відновіть дамп,
запустіть знову:

```bash
docker compose stop api
docker compose exec -T db sh -c 'gunzip -c /backups/daily/crm-20260901-040000.sql.gz | psql -U crm -d crm'
docker compose start api
```

Дамп містить інструкції `DROP ... IF EXISTS`, тому відновлюється поверх
наявних даних.

### На новий сервер

1. Встановіть CRM за інструкцією свого рівня, використавши **збережений** `.env`
   (або ті самі значення секретів у панелі). Версія має збігатися з версією, з
   якої зроблено дамп, або бути новішою.
2. Скопіюйте файл дампа в том:

   ```bash
   docker compose cp ./crm-20260901-040000.sql.gz db:/backups/restore.sql.gz
   ```

3. Відновіть за командами вище.
4. Якщо версія новіша за версію дампа, після відновлення перезапустіть API —
   міграції застосуються автоматично.

## Перевірка

Резервна копія, яку жодного разу не відновлювали, не є перевіреною. Раз на
кілька місяців відновлюйте останній дамп на тестовому сервері або локально в
режимі `--local` і переконуйтеся, що дані на місці.
