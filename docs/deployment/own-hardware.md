# Рівень 3. Власне обладнання та розширені конфігурації

Інструкція для технічних адміністраторів. Охоплює розгортання на власному
обладнанні — сервері в офісі, міні-ПК, ноутбуку — і нестандартні конфігурації:
доступ без публічної IP-адреси, інтеграцію з наявним реверс-проксі, зовнішню
базу даних.

Базові операції описані в [server.md](server.md); тут — лише відмінності.

## Коли це доречно

- Дані не повинні залишати приміщення організації.
- Немає стабільного інтернет-каналу, але є локальна мережа.
- Пробна інсталяція на робочому комп'ютері перед вибором хостингу.

Власне обладнання переносить на організацію відповідальність за живлення,
резервні копії та фізичну безпеку. Ці питання розглянуті нижче.

## Обладнання

| Компонент          | Рекомендація                                                   |
| ------------------ | -------------------------------------------------------------- |
| Комп'ютер          | Міні-ПК або офісний ПК; 4 ГБ пам'яті, SSD від 64 ГБ             |
| Живлення           | ДБЖ (UPS) з достатнім часом автономної роботи для коректного вимкнення |
| Мережа             | Дротове підключення; фіксована IP-адреса через резервування в DHCP маршрутизатора |
| Операційна система | Ubuntu Server LTS. Windows 10/11 з Docker Desktop — для пробних інсталяцій |

Ноутбук придатний для пробної інсталяції та невеликої команди, але не для
постійної роботи: режим сну, закрита кришка та оновлення системи переривають
доступ.

Налаштування ОС для постійної роботи: вимкнути режим сну та гібернацію,
увімкнути автоматичний вхід або автозапуск Docker, налаштувати автоматичне
ввімкнення після відновлення живлення в BIOS/UEFI.

## Встановлення в локальному режимі

Без публічного домену сертифікат Let's Encrypt отримати неможливо. Локальний
режим використовує вбудований центр сертифікації Caddy.

```bash
git clone https://github.com/uniia-ave-team/crm-with-ngos.git
cd crm-with-ngos && git checkout v1.0.0 && cd deploy
./install.sh --local
```

Скрипт запитає адресу, за якою відкриватиметься CRM. Варіанти:

| `DOMAIN`                    | Коли                                                    |
| --------------------------- | ------------------------------------------------------- |
| `localhost`                 | Пробна інсталяція на одному комп'ютері                  |
| `192.168.1.20`              | Доступ у локальній мережі за IP-адресою                  |
| `crm.local`                 | Є локальний DNS або записи в `hosts` на робочих місцях   |
| `crm.local, 192.168.1.20`   | Кілька адрес одночасно                                   |

Без інтерактивного вводу: `DOMAIN=192.168.1.20 ./install.sh --local`.

У `.env` записується `CRM_MODE=local`; `update.sh` враховує це автоматично.

### Довіра до сертифіката

Браузери показують попередження, доки кореневий сертифікат локального центру не
встановлений на робочому місці. Вивантажити його:

```bash
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./crm-root-ca.crt
```

Встановлення на робочих місцях:

- **Windows:** подвійний клік на файлі → «Встановити сертифікат» → «Локальний
  комп'ютер» → «Помістити всі сертифікати в наступне сховище» → «Довірені
  кореневі центри сертифікації». Або з правами адміністратора:
  `certutil -addstore -f Root crm-root-ca.crt`.
- **macOS:** відкрити файл у «Зв'язці ключів» → системна зв'язка → у
  властивостях сертифіката встановити «Завжди довіряти».
- **Linux (Debian/Ubuntu):**
  `sudo cp crm-root-ca.crt /usr/local/share/ca-certificates/ && sudo update-ca-certificates`.
  Firefox використовує власне сховище: Налаштування → Сертифікати → Імпортувати.
- **Android:** Налаштування → Безпека → Встановити сертифікат → сертифікат ЦС.
- **iOS:** відкрити файл, встановити профіль, потім Налаштування → Основні →
  Про пристрій → Довіра до сертифікатів.

Сертифікат дійсний доти, доки існує том `crm_caddy_data`. При його видаленні
центр сертифікації створюється заново, і сертифікат потрібно встановити
повторно.

## Доступ без публічної IP-адреси

Для роботи з CRM з-поза офісу без відкриття портів на маршрутизаторі
рекомендовано **Tailscale** — приватну мережу між пристроями організації.

1. Встановіть Tailscale на сервер і на пристрої користувачів; увійдіть в один
   обліковий запис організації.
2. Увімкніть MagicDNS у консолі Tailscale. Сервер отримає ім'я на кшталт
   `crm-server.tail1234.ts.net`.
3. Вкажіть це ім'я в `DOMAIN` (можна разом із локальною адресою через кому)
   і перезапустіть: `docker compose up -d --wait`.

Tailscale надає власні довірені сертифікати для імен `*.ts.net`, але для
одноманітності у локальному режимі використовується сертифікат Caddy; кореневий
сертифікат потрібно встановити на пристроях, як описано вище.

Альтернатива — Cloudflare Tunnel: публічний домен без відкритих портів. У цьому
разі TLS термінується на боці Cloudflare, а Caddy працює в локальному режимі.
Конфігурація тунелю виходить за межі цієї інструкції.

## Windows, macOS і Docker Desktop

Для пробної інсталяції на одному комп'ютері призначені скрипти
`deploy/windows/*.cmd` і `deploy/macos/*.command`, описані в
[quick-start.md](quick-start.md#варіант-а-на-власному-компютері). Вони
встановлюють CRM з `DOMAIN=localhost` і додають кореневий сертифікат у сховище
поточного користувача.

Для доступу з інших пристроїв мережі потрібна інша адреса в `DOMAIN`. На
Windows скрипти `install.sh` та `update.sh` виконуються в Git Bash або в
терміналі WSL; без них — вручну:

```powershell
Copy-Item .env.example .env
# заповнити .env: CRM_MODE=local, DOMAIN, POSTGRES_PASSWORD, AUTH_SIGNING_KEY
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --wait
```

Docker Desktop на Windows працює через WSL 2; увімкніть його під час
встановлення.

Обмеження:

- Порти 80 і 443 можуть бути зайняті IIS або іншими службами; перевірка —
  `netstat -ano | findstr ":443 "`.
- Docker Desktop має бути в автозапуску, а комп'ютер — не переходити в режим сну.
- Продуктивність дискових операцій нижча, ніж на Linux. Для постійної роботи
  рекомендовано Linux.

## Розширені конфігурації

Нестандартні налаштування задаються додатковим compose-файлом. Створіть у
`deploy/` файл, наприклад `docker-compose.custom.yml`, і вкажіть його в `.env`:

```
CRM_COMPOSE_EXTRA=docker-compose.custom.yml
```

`install.sh` та `update.sh` підключать його після основних файлів. Файл не
відстежується Git і зберігається між оновленнями.

### Резервні копії на зовнішній диск

Том `backups` замінюється прив'язкою до каталогу на змонтованому диску:

```yaml
volumes:
  backups:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /mnt/backup-disk/crm
```

Каталог має існувати до запуску. Це не скасовує потреби в копії за межами
приміщення — [backups.md](backups.md).

### Наявний реверс-проксі на портах 80/443

Якщо на сервері вже працює nginx, Apache або інший проксі, Caddy переводиться
на внутрішній порт без TLS, а зовнішній проксі спрямовує на нього трафік:

```yaml
services:
  caddy:
    ports: !override
      - "127.0.0.1:8081:80"

configs:
  caddyfile:
    content: |
      http://${DOMAIN} {
        encode zstd gzip
        handle /api/* {
          reverse_proxy api:8080
        }
        handle {
          reverse_proxy web:8080
        }
      }
```

Зовнішній проксі має термінувати TLS і передавати заголовки `Host`,
`X-Forwarded-For`, `X-Forwarded-Proto`. У `.env` `CRM_MODE` лишається `public`.

### Зовнішня база даних PostgreSQL

Вбудовані сервіси бази та резервних копій вимикаються, API отримує інший рядок
підключення:

```yaml
services:
  db:
    profiles: ["disabled"]
  db-backup:
    profiles: ["disabled"]
  api:
    depends_on: !reset []
    environment:
      ConnectionStrings__Default: Host=db.internal;Port=5432;Database=crm;Username=crm;Password=${POSTGRES_PASSWORD}
```

Потрібна PostgreSQL 16 або новіша. Резервне копіювання в цьому разі виконується
засобами зовнішнього сервера бази даних.

## Оновлення

`./update.sh` працює однаково в усіх режимах і підключає `CRM_COMPOSE_EXTRA`.
Загальні правила — [upgrading.md](upgrading.md).
