# Оновлення

Кожен реліз збирає обидва образи — API і вебклієнт — під одним номером версії.
Оновлення завжди означає перехід усієї інсталяції на новий номер; оновлювати
компоненти окремо не передбачено.

Міграції схеми бази застосовуються автоматично при запуску API.

## Загальні правила

**Перед оновленням — резервна копія.** `update.sh` створює її автоматично. При
оновленні через панель зробіть її вручну ([backups.md](backups.md)).

**Не перестрибуйте мажорну версію.** Послідовність `1.x` → `2.x` → `3.x`.
Міграції з попередньої мажорної версії видаляються через один цикл; API не
запуститься на схемі, яку не розпізнає.

**Читайте нотатки до релізу** на [сторінці релізів](https://github.com/uniia-ave-team/crm-with-ngos/releases).
Мінорні релізи (`1.4` → `1.5`) можуть містити зміни, що потребують дій
адміністратора; такі зміни виділені окремо. Патч-релізи (`1.4.1` → `1.4.2`) не
змінюють схему руйнівно і безпечні завжди.

**Не використовуйте автоматичні оновлювачі** на кшталт Watchtower. Вони
замінюють образи без резервної копії та без перевірки нотаток до релізу.

## Рівень 1. Власний комп'ютер

Інсталяція на комп'ютері використовує найновіший реліз; окремий номер версії
не задається.

1. Перегляньте нотатки до нового релізу.
2. Переконайтеся, що Docker Desktop запущений.
3. Двічі клацніть `deploy/windows/update.cmd` (Windows) або
   `deploy/macos/update.command` (macOS). Скрипт створює резервну копію,
   завантажує нову версію та перезапускає сервіси.
4. Дочекайтеся повідомлення про завершення й відкрийте `https://localhost`.

Якщо реліз змінює файли розгортання (про це сказано в нотатках), спершу
завантажте новий архів зі сторінки релізів і скопіюйте в його папку `deploy`
файл `.env` зі старої інсталяції, після чого запустіть `update` уже з нової
папки. Дані зберігаються в Docker і не залежать від папки з файлами.

Якщо після оновлення CRM не працює, створіть issue з текстом із вікна
оновлення. Резервна копія, зроблена перед оновленням, лишається в інсталяції в
каталозі `pre-update/` ([backups.md](backups.md)).

## Рівень 1. Dokploy

Гілка `stable` репозиторію завжди відповідає останньому релізу, а образи без
зазначеного номера версії — його ж збірці. Оновлення зводиться до повторного
розгортання.

1. Перегляньте нотатки до нового релізу.
2. Створіть резервну копію сервера в кабінеті провайдера (знімок або ручний
   backup), якщо автоматична остання копія старша за добу.
3. У Dokploy відкрийте сервіс `crm` → **Deploy**. Якщо реліз додає нові змінні
   середовища (сказано в нотатках), спершу додайте їх у вкладці
   **Environment**.
4. Дочекайтеся стану **Done** у **Deployments** і відкрийте CRM у браузері.

Для повернення до попередньої версії у вкладці **Environment** додайте рядок
`CRM_VERSION=1.0.0` з номером попереднього релізу та натисніть **Deploy**. Якщо
API не запускається через невідповідність схеми — відновіть копію за
[backups.md](backups.md#відновлення).

## Рівень 2. Portainer

1. Перегляньте нотатки до нового релізу.
2. Створіть резервну копію: **Containers** → `crm-db-backup-1` → **Console** →
   **Connect** → `/backup.sh`.
3. **Stacks** → `crm`. У полі **Repository reference** вкажіть новий тег,
   наприклад `refs/tags/v1.1.0`.
4. У розділі змінних середовища змініть `CRM_VERSION` на `1.1.0`.
5. Натисніть **Pull and redeploy**, підтвердьте.
6. У **Containers** дочекайтеся стану `running` для всіх сервісів і `healthy`
   для `web`, `db`, `db-backup`. Відкрийте CRM у браузері.

Якщо після оновлення CRM не працює: поверніть попередні значення reference та
`CRM_VERSION`, знову натисніть **Pull and redeploy**. Якщо API не запускається
через невідповідність схеми — відновіть копію з кроку 2 за
[backups.md](backups.md#відновлення), потім повторіть відкат.

## Рівень 2 і 3. Скрипт

```bash
cd crm-with-ngos
git fetch --tags
git checkout v1.1.0
cd deploy
./update.sh 1.1.0
```

`git checkout` нового тегу обов'язковий: реліз може змінити `docker-compose.yml`
(новий сервіс, нова змінна). Файл `.env` не відстежується Git і зберігається.

Скрипт:

1. Створює дамп бази в `pre-update/`.
2. Записує нову версію в `.env`.
3. Завантажує образи та перезапускає сервіси.
4. Чекає на справний стан усіх сервісів.

Якщо сервіси не піднялися, скрипт виводить команди відкату разом з іменем
створеної копії. Порядок: повернути попередню версію в `.env`, виконати
`docker compose up -d --wait`; якщо API не запускається — відновити копію з
`pre-update/`.

## Свідомий відкат

```bash
cd deploy
sed -i 's|^CRM_VERSION=.*|CRM_VERSION=1.0.0|' .env
docker compose up -d --wait
```

Міграції написані за принципом «спершу розширити, потім звузити»: реліз додає
нові структури й не видаляє старих, видалення відбувається в наступному релізі.
Тому попередня версія зазвичай працює з базою, яку новіша вже мігрувала.
Гарантії немає — тому копія створюється перед кожним оновленням.

## Оновлення Docker-образів сторонніх компонентів

PostgreSQL, Caddy і сервіс резервних копій оновлюються разом із релізами CRM:
їхні версії зафіксовані в `docker-compose.yml`. Перехід на нову мажорну версію
PostgreSQL виконується лише в мажорному релізі CRM і описується в нотатках до
нього окремою процедурою.
