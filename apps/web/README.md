# Вебклієнт

Клієнт на Ionic Angular. Каталог самодостатній: `package.json` і
`package-lock.json` розташовуються тут, а не в корені репозиторію. Спільного
workspace з `apps/api` немає. Пакет називається `Yavir`.

Застосунок має робочу оболонку (бокове меню, дев'ять сторінок, локалізація),
сторінку входу, яка вже працює з `apps/api`, сторінку запрошення колеги,
сторінку налаштувань профілю й сторінку «Адмін».
Вхід перевіряє підключення, веде через первинне налаштування системи
(адміністратор, організація), виконує вхід і підтримує сесію. Сесія — це
збережені в `localStorage` акаунти (див. «Акаунти»). Користувач може мати кілька
акаунтів: додає їх кнопкою «+» в меню акаунта й перемикається клацанням по
плитці. Сторінки «Календар», «Планер» і
«База знань» поки порожні заглушки без вмісту; «Колеги» має шапку й таблицю
зі зразковими рядками.

## Вимоги

Node.js **22.22.3 або новіший** (також підходять 24.15+ і 26+).

## Команди

Усі команди виконуються в `apps/web`.

```bash
npm install                        # встановити залежності
npm start                          # ng serve, http://localhost:4200
npm run build                      # production-збірка у www/
npm run watch                      # збірка з перезбиранням (development)
npm test                           # Vitest у режимі спостереження
npm run test:ci                    # Vitest, один прогін (для CI)
npm run lint                       # ESLint для src/**/*.ts і src/**/*.html
npm run lint:fix                   # ESLint з автовиправленням
npm run generate                   # generate:api + generate:languages
npm run generate:api               # клієнт API з openapi.json
npm run generate:languages         # список мов із src/assets/i18n/*.json
```

З кореня репозиторію те саме доступне через `just`: `just web`,
`just test-web`, `just web-ci`.

`npm start`, `npm run build`, тести й лінт спершу генерують потрібне: клієнт
API з `packages/api-contract/openapi.json` у `src/app/api/generated` (npm-хуки
`prestart`, `prebuild`, `pretest`, `pretest:ci`) і список мов
`src/app/core/i18n/languages.generated.ts` зі `scripts/generate-languages.mjs`
(ті самі хуки плюс `prelint`, `prelint:fix`). Обидва ігноруються git.

`ng build` кладе результат у `www/`, а не в `dist/`. Саме звідти `Dockerfile`
копіює статику для nginx. Каталог `www/` ігнорується git.

Production-образ локально: `just up` з кореня репозиторію, потім
<http://localhost:8080>. API, яке піднімає `just up`, слухає
`http://localhost:5065` і приймає запити й з `ng serve` (`:4200`), тож для
роботи з реальними даними .NET не потрібен: `just up`, потім `npm start`.

Бюджети production-збірки: початковий бандл — попередження від 2 МБ, помилка
від 5 МБ; стилі компонента — 4 і 8 КБ.

## Поточний стан

Створено:

- **Каркас і навігація.** `AppComponent` — оболонка застосунку: бокова панель
  (`core/layout/primary-nav`, десктопна колонка / мобільні верхня й нижня
  панелі) і друга контекстна панель (`core/layout/secondary-panel`) для
  сторінок «База знань», «Планер» і «Налаштування». Сторінки без бічного меню взагалі
  (наразі — `/login`, `/join` і `/relogin`) позначаються `data: { layout: 'none' }` у
  маршруті й читаються через `LayoutService.hideShell`; місце під мобільні
  панелі резервується лише всередині оболонки. Поки йде пошук чинного
  акаунта (старт застосунку, перехід на захищену сторінку), поверх усього
  показується повноекранний прелоадер (`shared/preloader`).
- **Дев'ять сторінок:** `calendar`, `planner`, `knowledge-base` (порожні заглушки з
  перекладеним заголовком), `colleagues`, `admin-panel`, `settings` (див.
  нижче), `login`, `join` і `relogin` — сторінки без бічного меню. На стартовій адресі `/`
  відбувається переадресація на `/login`. Пункти основного меню: Календар,
  Планер, База знань, Колеги і Адмін (іконка `hammer-outline`, адреса
  `/admin-panel`). «Колеги» показуються лише тим, у кого є
  `Permissions.ViewUser`. «Адмін» показується лише тим, у кого є **хоча б одне**
  з прав: `Permissions.UpdateNgo`, `Permissions.CreateLoginPageImages`,
  `Permissions.DeleteLoginPageImages` (права активного акаунта зі знімка в
  `localStorage`; поки їх не отримано, пункту нема). На телефонах шириною до
  400px підписи нижнього меню мають 10px і не переносяться, бо пʼять пунктів
  ділять ширину екрана. Кнопка «Зоря» (іконка `zoria.svg`) у бічній і
  мобільній верхній панелях поки без дії.
- **Сторінка входу** веде користувача через підключення, первинне
  налаштування системи й вхід. Якщо в `localStorage` є збережені акаунти,
  спершу шукається чинний (див. «Акаунти»): знайшовся — одразу перехід на
  `REDIRECT_URL` (зараз `/planner`), форми не показуються, а поки пошук
  триває, видно «Перевіряємо підключення…»; не знайшовся, але акаунти
  лишились — перехід на `/relogin`. Якщо акаунтів нема взагалі,
  перевіряється підключення: немає — форма адреси сервера; є —
  запитується `GET /api/v1/system/status`. Далі за статусом і наявністю
  активного акаунта (він з'являється, коли користувач щойно ввійшов або
  зареєстрував адміністратора на цій сторінці). Рядки перевіряються зверху
  вниз; `—` означає «неважливо»:

  | `isSetupComplete` | `hasAdmin` | `hasNgo` | Активний акаунт | Результат                       |
  |-------------------|------------|----------|-----------------|---------------------------------|
  | `true`            | —          | —        | немає           | форма входу                     |
  | `true`            | —          | —        | є               | перехід на `REDIRECT_URL`       |
  | `false`           | `false`    | —        | —               | форма реєстрації адміністратора |
  | `false`           | `true`     | `false`  | є               | форма створення ГО              |
  | `false`           | `true`     | `false`  | немає           | форма входу                     |
  | `false`           | `true`     | `true`   | —               | помилка налаштування системи    |

  Якщо статус отримати не вдалося, показується форма входу. Помилка
  налаштування системи має текст «Сталася помилка при налаштуванні системи.»

  - **Форма входу** (зображення зліва, форма справа; на вузьких екранах лише
    форма): пошта й пароль. `POST /api/v1/auth/login`, вхід зберігається
    як акаунт (адреса сервера, токени, пошта), запитується статус системи: немає ГО — форма створення ГО, є — перехід
    на `REDIRECT_URL`. Лого Явору — мобільне лого меню (за мовою й темою),
    лого Унії — `Uniia.svg` для української, кримськотатарської й білоруської,
    `Uniia_en.svg` для решти; лого партнерів і зображення — зі світлими
    (`assets/logos`) і білими (`assets/logos_white`) варіантами для темної
    теми. Зображення збоку форми — випадкове з тих, що завантажені в системі:
    `GET /api/v1/loginpageimages/random` (публічний запит, токен не потрібен),
    робиться один раз на сервер, коли показано саму форму входу. Поки запит
    іде, а також коли зображень нема (`404`), сервер не відповів чи
    зображення не завантажилось, показується стандартне
    `assets/login_image.jpg`.
  - **Форма адміністратора:** пошта, прізвище, імʼя, по батькові (необовʼязкове,
    у запит іде `null`, якщо порожнє), пароль і його повтор;
    `POST /api/v1/users`, потім одразу `POST /api/v1/auth/login` з тими самими
    даними. Пароль має відповідати правилам сервера (`IdentityOptions` в
    налаштуваннях API): від 8 символів, велика й мала латинські літери,
    цифра та спецсимвол; умови виведено списком під полем пароля й
    відмічаються під час введення, під повтором відмічається збіг паролів.
  - **Форма ГО:** назва й логотип (поле перетягування з превʼю та круглою
    кнопкою видалення). `POST /api/v1/ngo` (лише назва); якщо
    обрано логотип, після цього першого запиту йде `POST /api/v1/ngo/logo`
    (`multipart/form-data`, поле `file`) із самим зображенням, потім перехід
    на `REDIRECT_URL`. Організація створюється один раз: якщо логотип не
    завантажився, показується помилка, назва стає лише для читання, а
    повторне «Продовжити» повторює тільки завантаження логотипа (або, якщо
    файл прибрали, одразу веде далі).
  - **Кнопка «змінити адресу сервера»** (кругла, з іконкою сервера, праворуч
    угорі кожної форми, крім кроку адреси): спершу один запит `GET /health`
    на поточний сервер, потім повне очищення `localStorage` і форм та
    повернення на крок адреси; якщо сервер був здоровий, його адресу
    підставлено в поле. Кнопка скидає все, що збережено в браузері для
    застосунку: адресу сервера, мову, акаунт, який зараз налаштовується
    (наприклад, щойно створеного адміністратора, коли відкрито форму ГО), і
    застарілі акаунти. Інших акаунтів на цій сторінці бути не може: чинний
    перекинув би на `REDIRECT_URL`, а застарілі чи недоступні — на `/relogin`.
  - **Помилки:** валідація форм — до будь-якого запиту. Помилки полів
    показуються під ними, а відповіді сервера (і помилка прізвища у формі
    адміністратора) — окремим блоком над формою.
  - Усім полям і кнопкам задано `tabindex`, бо в Safari без нього не працює
    табуляція.
- **Сторінка запрошення** (`/join?token=…`) — куди веде посилання з вікна «Додати
  колегу». Без стражів і без бічного меню. Працює із сервером за доменом сторінки
  (`ConnectionService.pageServerUrl`), а не активного акаунта: колега може вже мати
  акаунт деінде, а запрошення — на цей сервер. Кроки:
  1. `GET <сервер>/health`. Сервера нема — червоний блок «Ми не можемо знайти
     сервер. Спробуйте з локальної мережі своєї ГО або зверніться до
     адміністратора.» і посилання «На головну» (на `/login`);
  2. `GET /api/v1/invitations/validate?token=…` (без токена в посиланні запиту нема).
     Будь-яка невдача (прострочений, використаний чи зіпсований токен, помилка
     сервера) — блок «Надане посилання неактивне або сталася помилка. Зверніться до
     адміністратора.» з тим самим посиланням «На головну»;
  3. форма: пошта з відповіді (неактивне поле), прізвище, імʼя, по батькові
     (необовʼязкове, порожнє йде в запит як `null`), пароль і його повтор
     (`app-password-fields`, правила як у формі адміністратора; помилка прізвища,
     як там, — блоком над формою). Стилі й структура — з `/login`;
  4. «Зареєструватися» — `POST /api/v1/invitations/accept`. У відповіді пара
     токенів: `AuthService.adoptTokens` додає акаунт як активний, далі перехід на
     `REDIRECT_URL`. Помилка — червоний блок над формою (`join.saveError.*`),
     форму можна надіслати ще раз. Відповідь на перевірку для старого токена
     (посилання змінили, поки йшов запит) ігнорується. Тексти — `join.*`.
- **Сторінка повторного входу** (`/relogin`) — куди веде відсутність доступних
  акаунтів, коли збережені ще є. Без стражів і без бічного меню. Вибір акаунта у
  стилі Google: зображення зліва (стандартне `assets/login_image.jpg`), як на
  `/login`, справа лого «Явір», заголовок, список збережених акаунтів (у порядку
  додавання, також застарілих і недоступних) і кнопка «Додати акаунт». Рядок —
  аватар (`app-account-avatar`: значок стану, логотип ГО) і підпис: у першому рядку
  «ПІБ — Назва ГО», у другому (якщо треба) «Відсутнє підключення до серверу» чи
  «Сеанс закінчився» (ті самі тексти, що в підказці плитки меню; без імені й ГО —
  «Акаунт»). Кнопка додавання — той самий вигляд і підпис, що в меню акаунтів. Якщо
  акаунтів нема взагалі (також коли вони зникнуть, поки сторінка відкрита),
  переадресація на `/login`.
  - **При відкритті:** для кожного недоступного, але не застарілого акаунта
    пробується обмін токенів (`AuthService.refreshStored`): вдалося — токени нові,
    `unavailable` знято; токени відхилено — акаунт `outdated`; сервер мовчить —
    без змін.
  - **Вибір у списку:** доступний або недоступний, але не застарілий акаунт —
    `AccountRestoreService.activate`: успіх — він активний і відкривається
    `REDIRECT_URL`, помилка — форма з його даними. Застарілий (з `unavailable` чи
    без) — одразу форма. «Додати акаунт» — форма для нового. Поки йде
    перемикання, повторні клацання ігноруються.
  - **Форма** (`relogin/relogin-form`, на місці списку; зображення зліва
    лишається): «Назад» — до списку; заголовок «Вхід в акаунт» і смітник на одному
    рядку (для нового акаунта смітника нема): смітник видаляє дані акаунта з
    памʼяті й повертає до списку (не лишилось акаунтів — `/login`). Адреса сервера
    — акаунта або домену сторінки (для нового); після кожної зміни (після паузи
    0,5 с, перша перевірка одразу) `GET /health`, і лише для здорового сервера з
    нього береться випадкове зображення (`random(server)`); інакше під полем
    повідомлення про недоступність сервера й стандартне зображення. Пошта — акаунта
    або порожня; пароль. «Ввійти» активна лише для здорового сервера; вхід
    оновлює акаунт (пошта збіглася з поштою акаунта; інакше додає новий), робить
    його активним і відкриває `REDIRECT_URL`, а помилка лишає форму з
    повідомленням над нею. «Забули пароль?» поки без дії.
- **`ConnectionService`** (`core/connection`) — визначає, до якого сервера
  підключатися, і перевіряє його:
  - адреса сервера: надана користувачем (зберігається в памʼяті, а після
    входу — у записі акаунта) має пріоритет і без запасного варіанта; якщо її
    нема — домен, з якого відкрито сторінку. Порт за замовчуванням — 5065;
  - перевірка `GET <сервер>/health` (таймаут 5 с) дає стан `healthy`,
    `unhealthy` або `unreachable`; результат виводиться в консоль;
  - `loadSystemStatus()` запитує `GET <сервер>/api/v1/system/status`;
  - `pageServerUrl` — сервер за доменом сторінки (`<протокол>://<домен>:5065`)
    незалежно від акаунтів і наданої адреси (для `/join`); `probeApi(server?)` —
    одноразова перевірка `GET /health` поточного чи заданого сервера, що не чіпає
    стан сервісу; `parseServerAddress()` розбирає введену адресу в URL.
- **Стражі сторінок** (`core/auth`, `core/connection`). Усі сторінки, крім
  `/login`, `/join` і `/relogin`, проходять `authGuard`, а потім `connectionGuard`. Маршрути мають
  `runGuardsAndResolvers: 'always'`, тому стражі спрацьовують при **кожній**
  зміні сторінки (також між вкладками налаштувань), а не лише коли маршрут
  активується вперше. Права користувача (`permissions`) не приходять у
  відповіді `/users/me`: після кожного його успіху `CurrentUserService`
  окремо запитує `GET /users/me/permissions` і записує їх у знімок акаунта;
  інтерфейс (меню, сторінка «Адмін») читає їх звідти.
  - `authGuard`, коли поточний акаунт уже підтверджено в цій сесії сторінки
    (профіль у памʼяті): пускає одразу, а у фоні перепитує профіль —
    `GET /users/me`, разом із ним права й назву ГО (див. `CurrentUserService`).
    Так зміни в БД (дані профілю, права, назва й логотип ГО) потрапляють в
    інтерфейс без перезавантаження. Запит сторінку не блокує: невдача лишає
    попередні дані, недійсні токени обробляє `authInterceptor` (оновлення або
    вихід на `/login`).
  - Коли профілю ще нема (перше відкриття, перезавантаження, одразу після
    входу): шукає чинний акаунт серед збережених так само, як сторінка входу,
    і перший знайдений стає поточним (запит `/users/me` робить сам пошук, тож
    другого немає; одразу після нього, як і на кожному шляху, йде
    `GET /users/me/permissions`: права пишуться в запис акаунта, і меню «Адмін»
    будується з них без перезавантаження). Результат пошуку: `restored` —
    пускає; інакше доступного акаунта нема: переадресація на `/relogin`,
    якщо збережені акаунти є, і на `/login`, якщо їх нема взагалі.
  - `connectionGuard` додатково вимагає, щоб API за поточною адресою
    відповідав, інакше теж `/login?error=no-connection`.
  - `requireAnyPermission([...])` (`core/auth/permission.guard.ts`) стоїть
    третім на маршрутах `/admin-panel` (`ADMIN_PANEL_PERMISSIONS`) і
    `/colleagues` (`COLLEAGUES_PERMISSIONS`, тобто `ViewUser`): пускає лише
    того, у кого є **хоча б одне** з перелічених прав, інакше переадресація на
    `REDIRECT_URL`. Стражі маршруту
    стартують одночасно, тож цей сам чекає входу (пошук акаунта спільний з
    `authGuard`; відмову входу оформлює `authGuard`, а цей лише не пускає).
    Далі вирішують свіжі права: профіль перепитується (`GET /users/me`) і
    страж чекає, поки `/users/me/permissions` потраплять у знімок акаунта,
    тож права, відкликані в БД, діють одразу. Якщо оновити не вдалося (сервер
    не відповів), лишаються збережені права. Цим стражем сторінка
    відкривається із затримкою на два запити (на відміну від решти, де запит
    іде у фоні).
- **Акаунти** (`core/accounts`):
  - `AccountsService` — сховище акаунтів у `localStorage`: запис на акаунт
    (`yavir.account.<id>`), індекс (`yavir.accounts`) і вказівник на активний
    (`yavir.activeAccount`). Запис містить адресу сервера, токени, пошту,
    ознаку користувача (`identity`), знімок профілю (прізвище, імʼя, по батькові, аватар,
    назва та посилання на логотип ГО, їхні мініатюри `avatarThumb` і
    `ngoLogoThumb`), права користувача (`permissions` —
    список рядків із `GET /users/me/permissions`, оновлюється разом із
    профілем при кожній зміні сторінки), ролі користувача (`roles` — список
    `{id, name}` з поля `roles` відповіді `GET /users/me`, оновлюється разом
    із профілем; елементи без рядкових `id` й `name` і не-масив у сховищі
    читаються як порожній список), незалежні прапорці `outdated` (сервер
    відхилив токени) і `unavailable` (сервер не відповів) та час отримання токенів (`tokensIssuedAt`). `id` акаунта —
    домен сервера лише латинськими літерами та хеш сервера й користувача
    (наприклад, `localhost-3ee638bc`); при збігу хешу додається суфікс `-2`,
    `-3`. Зміни в інших вкладках підхоплюються через подію `storage`.
    `add(input, replaceId?)` додає акаунт і робить його активним; той самий сервер
    і користувач — той самий акаунт, його токени оновлюються. `replaceId` — ключ
    акаунта, який перезаписується (сервер, користувач, токени) без створення
    нового: `id`, порядок і дата додавання лишаються; знімок профілю лишається,
    лише якщо це той самий користувач на тому ж сервері; інший запис цього
    користувача на цьому сервері видаляється. `markOutdated(id)` позначає акаунт
    `outdated` (і знімає `unavailable`), `markUnavailable(id)` — `unavailable`,
    `remove(id)` видаляє. Якщо такий акаунт був активним, активного більше нема:
    інший сам не підхоплюється. Памʼять не очищається (це робить лише «змінити
    адресу сервера» на `/login`; вихід видаляє лише активний акаунт);
  - `AccountRestoreService` — пошук чинного акаунта. Перший прохід — доступні
    акаунти (не `outdated`, не `unavailable`), активний першим; перший, що
    пройшов `/health`, токени (за потреби оновлюються) і `GET /users/me`, стає
    активним. Не пройшов: токени відхилено — `outdated`, сервер мовчить —
    `unavailable`. Доступного не знайшлось — другий прохід: недоступні, які такими
    були ще до пошуку (щойно недоступні не повторюються), перевіряються знову,
    кожен із `/health` власного сервера; успішний стає активним, його
    `unavailable` знімається. Застарілі пропускаються. Не пройшов жоден —
    активного нема, акаунти й токени лишаються в памʼяті. `activate(id)`
    перемикає на акаунт (клацання по плитці): робить його активним і перевіряє так
    само (`/health`, токени, `/users/me`). Успіх — лишається активним, `outdated` і
    `unavailable` знімаються; ні — активним повертається попередній, а цей
    позначається: токени відхилено — `outdated`, сервер не відповів —
    `unavailable`; профіль попереднього підтягується знову. На цей час, як і під
    час пошуку, вмикається `searching`.
- **Сесія й токени** (`core/auth`):
  - `AuthService` — вхід та токени активного акаунта (access і refresh лежать
    у його записі); обмін токенів (`POST /api/v1/auth/refresh-token`)
    потребує обох. Refresh-токен одноразовий, тому обмін іде в одному
    екземплярі: у межах вкладки — один спільний запит, між вкладками — Web
    Lock; нову пару, записану іншою вкладкою, підхоплюють зі сховища (подія
    `storage`), а не стирають. Невдале оновлення (400/401) позначає акаунт
    `outdated`. `expireSession(accountId, failure)` завершує сесію акаунта, якому
    не вдалося оновити токени: акаунт лишається (`outdated` для відхилених токенів,
    `unavailable` для мовчазного сервера), активного нема, перехід на `/relogin`,
    якщо за цей час активним не став інший. `login(email, password, server?, replaceAccountId?)` входить на
    заданому сервері (за замовчуванням поточному); `adoptTokens` додає акаунт із
    пари токенів і робить його активним (його ж викликає сторінка `/join`);
  - `authInterceptor` — додає `Authorization: Bearer <accessToken>` до
    запитів до `/api/...` (крім входу, виходу, оновлення токенів, статусу
    системи, `GET /loginpageimages/random` і `POST /users`); прострочений за `exp` токен оновлює до запиту, а на 401 оновлює токени й повторює запит один раз. Якщо оновити токени не вдалося —
    сесія акаунта завершується (`expireSession`): акаунт лишається з позначкою,
    активного нема, перехід на `/relogin`;
  - `SessionService` — у фоні оновлює токени перед завершенням терміну
    access-токена (також коли вкладка знову стає видимою). Окремо оновлює
    токени **неактивних** акаунтів, у яких минула половина терміну
    refresh-токена: після завершення пошуку акаунта, при поверненні вкладки у
    фокус і раз на годину. Термін refresh-токена клієнт не знає (сервер його не
    віддає), тому припускає 7 днів, як у налаштуваннях API за замовчуванням.
    Відхилені токени позначають акаунт застарілим, мережева помилка нічого не
    змінює. Якщо токени зникли, а ми не на `/login` чи `/relogin`, переносить на
    `/relogin` (акаунти лишились, але активного нема) або на `/login` (під час
    пошуку акаунта ця перевірка мовчить);
  - `CurrentUserService` (`core/users`) — `GET /users/me`: підтверджує вхід і
    дає профіль для меню та форм, записує знімок профілю (разом із ролями
    користувача, `roles`), назву й посилання на логотип ГО в запис акаунта. Разом з кожним таким запитом іде
    `GET /users/me/permissions`: права пишуться в запис акаунта
    (`permissions`) і доступні сигналом `permissions`; невдалий запит лишає
    попередній список. `ensure()` не робить запиту, якщо профіль уже
    завантажено, а `reload()` перепитує його завжди (це викликає `authGuard`
    при зміні сторінки). Якщо активний акаунт змінила інша вкладка (подія
    `storage`), профіль нового акаунта запитується одразу, а не при наступній
    зміні сторінки; під час пошуку акаунта й перемикання по плитці цього не
    робиться. Тимчасове перемикання активного акаунта (пошук, `activate`) профіль
    не скидає: `user` лишається профілем попереднього акаунта, а `profileLoaded`
    показує, чи профіль належить активному. Рейл, пункти меню й активна плитка
    слідують за акаунтом, який оновлюється лише після завершення перемикання.
    `permissionsSettled()` завершується, коли права з
    останнього запиту вже у знімку акаунта (на нього чекає
    `requireAnyPermission`). `applyLocal()` застосовує збережені зміни без
    запиту.
    Кожен із цих шляхів застосовує `preferredLanguage` профілю до мови
    інтерфейсу (див. «Локалізація»);
  - `UsersService` (`core/users`) — створення користувача, `GET /users`
    (сторінка колег: `id`, пошта, імʼя й прізвище, `hasNextPage`),
    `GET /users/me/permissions`, `PUT /users/me` (оновлення профілю),
    `POST /users/me/avatar` (завантаження аватара) і
    `POST /users/me/password` (зміна пароля);
  - `NgoService` (`core/ngo`) — створення організації (лише назва),
    завантаження логотипа (`POST /api/v1/ngo/logo`, після нього
    організація читається заново), оновлення назви (`PUT /api/v1/ngo`; успіх
    оновлює назву в знімку акаунта, логотип лишається) і читання її
    назви та посилання на логотип;
  - `InvitationsService` (`core/invitations`) — `POST /api/v1/invitations`
    (`invite(email, roleIds)`: токен і `expiresAt`), `GET …/validate` (пошта
    запрошення) і `POST …/accept` (реєстрація колеги, віддає пару токенів); сервер
    для двох останніх задається явно;
  - `ProtectedImageService` (`core/http`) і директива `appProtectedSrc`
    (`shared/protected-src`): `GET` логотипа ГО й аватара вимагають токен, тож
    звичайний `<img src>` дав би 401. Зображення за `/api/` активного сервера
    (крім публічних `loginpageimages`) завантажується через `HttpClient`
    (токен додає інтерцептор) і кладеться в `src` як `blob:`; помилка
    завантаження викликає `error` елемента, тож працюють повернення до літер
    чи порожній блок. Використовується в аватарі (`app-avatar`), значку
    логотипа в меню акаунта та формі організації. Кеш у памʼяті належить
    сесії: при зміні активного акаунта (вихід, вхід, перемикання) він
    очищується, щоб закрите зображення одного користувача не потрапило до
    іншого без запиту до сервера. Кожне зображення, що показується, береться
    директивою в користування й віддається при зміні адреси чи знищенні
    елемента; кеш тримає не більше 30 повнорозмірних зображень, а при
    переповненні звільняє лише ті, що не використовуються, починаючи з
    найдавніше використаних, тож зображення на екрані не зникає;
  - `ThumbnailService` (`core/images`): стискає зображення до квадрата
    (аватар 96×96 з обрізанням по центру, логотип 64×64 цілком, прозорість
    зберігається) у `data:`-посилання WebP. Мініатюри лежать у записі акаунта
    (`avatarThumb`, `ngoLogoThumb`: адреса, з якої зроблено, і саме
    зображення). Їх робить `CurrentUserService` для активного акаунта при
    кожному оновленні профілю й організації, але лише коли змінилась адреса
    зображення (`?v=…`); мініатюри неактивних акаунтів у фоні не оновлюються.
    Плитки в меню акаунтів малюються з них без запитів, бо закрите
    зображення можна завантажити лише з токеном активного акаунта; мініатюра
    зі старої адреси не використовується, а видаляються мініатюри лише разом
    з акаунтом;
  - `LoginPageImagesService` (`core/login-page-images`) —
    `GET /api/v1/loginpageimages` (одна сторінка за запит, відносні
    посилання перераховуються від адреси сервера), `DELETE …/{id}` (`404`
    вважається видаленим), `POST` (`multipart/form-data`, поле `file`;
    повертає `id`) і `GET …/random` (випадкове зображення для сторінки входу,
    публічний запит; `random(server?)` питає й сервер, що ще не став поточним).
- **«Вийти».** Видаляє лише активний акаунт (запис, індекс, вказівник активного;
  мова й інші акаунти лишаються) і відкликає його refresh-токен
  (`POST /api/v1/auth/logout`). Далі та сама перевірка, що й при вході на
  сторінку: знайшовся інший чинний акаунт — він стає активним і відкривається
  `REDIRECT_URL`; нема — `/relogin`, якщо акаунти ще є, інакше `/login`. Повне
  очищення `localStorage` лишилось лише в «змінити адресу сервера» на `/login`.
- **Додавання акаунта.** Кнопка «+» в меню акаунта відкриває вікно «Додати акаунт»
  (`core/layout/add-account` на `shared/modal`): хрестик, адреса сервера
  (початково поточна, змінюється), пошта, пароль, «Ввійти» й «Забули пароль?» (поки
  без дії). Стилі й тексти — з форми входу (`login.form.*`, `login.step1.*`).
  Виклик `open(email?, accountId?, server?)`: `email` вписується в поле пошти,
  `server` — у поле адреси замість поточного, `accountId` — ключ збереженого
  акаунта. Якщо ключ є, заголовок вікна «Ввійти в акаунт» (а не «Додати акаунт»), а
  поруч із хрестиком стоїть смітник: він видаляє цей акаунт з памʼяті (запис,
  індекс, токени; решта памʼяті й інші акаунти лишаються) і закриває вікно.
  «Ввійти»: 1) `GET /health` за адресою — відповіді нема: помилка під
  заголовком; 2) `POST /api/v1/auth/login` на цьому сервері; 3) ключ і пошта входу
  збігається (без урахування регістру) з поштою акаунта за ключем — цей акаунт
  перезаписується, а не додається новий; 4) акаунт, у який ввійшли, стає активним,
  вікно закривається, підключення перевіряється на його сервері, відкривається
  `REDIRECT_URL` (зі стражами заново). Помилки адреси, пошти й пароля — під
  полями, відповіді сервера — блоком над ними; форму можна надіслати ще раз.
- **Меню акаунта.** Аватар у бічній панелі відкриває спливаюче вікно
  (`shared/popover`), а в ньому `core/layout/account-menu`: список акаунтів,
  кнопка додавання, «Налаштування профілю» й «Вийти». Колір аватара без
  зображення рахується з імені, прізвища й назви ГО (`shared/avatar`, алгоритм
  у `avatar-color.ts`, контраст ≥ 4.5:1 і з білим, і з чорним). Список
  акаунтів береться зі збережених у `localStorage` (знімок профілю й ГО в
  записі акаунта; аватар і значок логотипа малюються з мініатюр у записі, без
  запитів), у порядку додавання; активний має білу
  рамку; значок ліворуч унизу за прапорцями: `unavailable` — жовта
  `sync-circle`, `outdated` (з `unavailable` чи без) — червона `alert-circle`;
  аватар сірий лише в `outdated`: літери на сірому тлі, а зображення (якщо є) в
  градаціях сірого. При наведенні браузер показує
  підказку (`title`): у першому рядку «ПІБ — Назва ГО», у другому (якщо треба)
  «Відсутнє підключення до серверу» (`unavailable`, має перевагу) або «Сеанс
  закінчився» (`outdated`).
  Значок логотипа ГО праворуч унизу показується, коли в ГО є логотип (мініатюра
  в записі акаунта); без логотипа плитка лишається без значка. Нижче
  «Налаштування профілю» (веде на `/settings`, відкриває «Особисті дані») й
  «Вийти». Клацання по плитці закриває меню й:
  - активний акаунт — нічого більше;
  - чинний (`outdated: false`) — перемикання (`AccountRestoreService.activate`) і
    перехід на `REDIRECT_URL` (зі стражами заново);
  - застарілий через відхилені токени (`outdated`, не `unavailable`) — вікно
    «Додати акаунт» із його сервером, поштою й ключем (збіглася пошта — акаунт
    перезапишеться), без спроби підключитися;
  - недоступний (`unavailable`, разом із `outdated` чи без) — повторна спроба
    (`activate`: сервер, оновлення токенів, профіль): вдалася — акаунт знову
    чинний і активний; ні — вікно «Додати акаунт»;
  - чинний, який при перемиканні виявився недійсним, — теж вікно «Додати акаунт»;
    активним лишається попередній.
- **Налаштування** (`/settings`). Друга бічна панель «Мої налаштування»
  (`core/layout/secondary-panel`) з пунктами-посиланнями; кожна вкладка має
  власну адресу: `/settings/personal-data` («Особисті дані», її відкриває й
  `/settings`), `/settings/password` («Зміна паролю»),
  `/settings/notifications` («Сповіщення»). Вкладки — окремі сторінки в
  `router-outlet` сторінки `settings`; спільні стилі форм —
  `settings/settings-section.scss`. Пункт «Сповіщення» приховано глобальним
  класом `.planned` (`src/global.scss`): елемент
  лишається в розмітці, але не показується, доки функція не готова.
  - **Дані профілю.** Власного запиту при відкритті вкладка не робить: поля
    беруться з профілю поточного користувача (`GET /api/v1/users/me`, який
    `authGuard` перепитує при кожній зміні сторінки й який оновлює знімок
    профілю в записі акаунта). Поля:
    прізвище, імʼя, по батькові, назва посади, номер телефону, екстренний
    контакт, країна перебування, мова інтерфейсу, займенники, аватар (PNG,
    WebP, JPEG, JPG або GIF до 20 МБ; інший тип відхиляється помилкою під
    блоком аватара) (пошти на сторінці нема: змінити її цим запитом API не
    дозволяє). Обовʼязкові (позначені `*`): прізвище, імʼя, займенники; решта
    необовʼязкові. Займенники — радіокнопки «Вона/її»,
    «Він/його», «Вони/їх» та «Інше» (з полем для свого варіанта); текст і
    категорія (`PronounCategory`: 1 — чоловічі, 2 — жіночі, 3 — нейтральні)
    передаються окремими полями. Номер телефону перевіряється на клієнті
    (`shared/phone`); порожній необовʼязковий рядок передається як `null`.
    «Зберегти» → `PUT /api/v1/users/me` (жодних прав не потрібно, лише
    авторизація); помилки полів показуються під ними, відповідь сервера —
    блоком зверху, після відповіді сторінка прокручується вгору. Поле «Мова
    інтерфейсу» будується зі списку мов (див. «Локалізація»). Якщо обрано файл
    аватара, після успішного `PUT` іде додатковий запит
    `POST /api/v1/users/me/avatar` (`multipart/form-data`, поле `file`; лише
    авторизація) із самим зображенням, а потім профіль перечитується
    (`GET /users/me`). Файл не обрано — цього запиту нема. Результат
    показується після обох запитів; невдача завантаження — червоний блок «Дані
    збережено, але аватар не змінено: …» (тексти в
    `settings.personal.result.avatar.*`), файл лишається обраним для повторної
    спроби. `PUT /users/me` аватара не містить і не змінює. Відповідність
    текстів займенників категоріям — припущення клієнта.
  - **Зміна паролю.** Поле поточного пароля, новий пароль і повтор
    (`shared/password-fields`, правила в `password-rules.ts`: від 8 символів,
    велика й мала латинські літери, цифра та спецсимвол; умови відмічаються
    під час введення). `POST /api/v1/users/me/password`; пароль не логується. Повні
    правила перевіряє сервер (`400` показується як «Невдала спроба…»), клієнт
    лише дає швидкий відгук. Результат — блок: червоний для помилки, зелений
    для успіху.
- **Адмін** (`/admin-panel`). Сторінка з формою організації; весь вміст за
  правами користувача (права з `GET /users/me/permissions`, зі знімка акаунта;
  оновлюються при кожній зміні сторінки). Саму сторінку пускає
  `requireAnyPermission` (див. «Стражі сторінок»); блоки всередині (права
  наведено без префікса `Permissions.`):

  | Що на сторінці                   | Коли показується                                          |
  |----------------------------------|-----------------------------------------------------------|
  | Назва й логотип організації      | є `UpdateNgo`                                             |
  | Галерея зображень сторінки входу | є `CreateLoginPageImages` **або** `DeleteLoginPageImages` |
  | Кнопка видалення на зображенні   | є `DeleteLoginPageImages`                                 |
  | Плитка додавання в кінці галереї | є `CreateLoginPageImages`                                 |

  Заголовок «Адмін» і одна кнопка «Зберегти» (під галереєю, спільна на всю
  форму) показуються завжди; кнопка блокується на час запиту й має текст
  «Зберігаємо…». Частини форми незалежні, кожну веде своє право: назву й
  логотип — лише `UpdateNgo`, завантаження зображень — лише
  `CreateLoginPageImages`, видалення — лише `DeleteLoginPageImages`.
  - **Назва** — обовʼязкове поле до 200 символів; початкове значення —
    `ngoName` зі знімка акаунта, і воно підхоплює оновлення, поки назву не
    змінювали.
  - **Логотип** — мініатюра 120×120 з вибором файлу (PNG, WebP, JPEG, JPG,
    GIF або SVG до 2 МБ; ті самі правила, що в логотипа на сторінці входу;
    типи задано в `core/images/image-types.ts`, розмір і довжину назви — у
    `core/ngo/logo-rules.ts`); обране зображення одразу показується в
    превʼю. Поки логотипа нема (або він не завантажився), показується порожній
    блок із пунктирною рамкою без літер і без заокруглення кутів.
  - **Збереження.** Кнопка одна, але запити частин незалежні (адреси
    відносно `/api/v1`, права без префікса `Permissions.`):

    | Запит                          | Право                   | Коли надсилається            |
    |--------------------------------|-------------------------|------------------------------|
    | `PUT /ngo` (назва)             | `UpdateNgo`             | назва не порожня й змінилася |
    | `POST /ngo/logo` (логотип)     | `UpdateNgo`             | обрано файл                  |
    | `DELETE /loginpageimages/{id}` | `DeleteLoginPageImages` | є видалені зображення        |
    | `POST /loginpageimages`        | `CreateLoginPageImages` | є додані файли               |

    Порядок: спершу назва (`PUT /api/v1/ngo` з `{ name }`, логотип не змінює;
    лише якщо назва змінилася; назва без пробілів по краях), потім логотип
    (`POST /api/v1/ngo/logo` із самим зображенням, лише якщо обрано файл і
    `PUT`, якщо він був, вдався), потім видалення, потім завантаження
    галереї. Після успішного завантаження логотипа організація читається
    заново (`GET /api/v1/ngo`), нове посилання потрапляє в знімок акаунта, а
    обраний файл і превʼю забуваються. Порожня назва блокує `PUT` і логотип
    (помилка під полем), галерея зберігається все одно. Невдача однієї групи
    не зупиняє іншу; в межах групи запити йдуть по одному й зупиняються на
    першій невдачі.

    Результат — блок над формою з кількома рядками: форма може бути
    збережена не повністю, тож перелічується, що саме змінилося й що не
    вдалося.

    | Рядок                                              | Коли зʼявляється                           |
    |----------------------------------------------------|--------------------------------------------|
    | «Назву організації змінено.»                       | назва змінилась, `PUT` вдався              |
    | «Логотип організації змінено.»                     | файл обрано, `POST /ngo/logo` вдався       |
    | «Зображення сторінки входу змінено.»               | у галереї щось збережено                   |
    | «Назву й логотип організації не змінено: …»        | `PUT` не вдався; логотип не надсилається   |
    | «Логотип організації не змінено: …»                | `POST /ngo/logo` не вдався; файл лишається |
    | «Зображення сторінки входу змінено не повністю: …» | запит галереї не вдався                    |

    Причини: `400` — сервер не прийняв дані, `401` — сесію завершено, `403` —
    недостатньо прав, відсутність відповіді — сервер не відповідає, інше —
    «спробуйте ще раз». Блок зелений, коли всі рядки успішні, і **червоний,
    якщо є хоч одна невдача** (успішні рядки в ньому теж видно). Нічого не
    змінювалось — блоку нема (і `PUT` не йде); блок зникає, щойно змінюють
    назву чи обирають файл. Тексти — у `admin.result.*` мовного файлу.

    Після успіху `PUT` назва записується в знімок акаунта в `localStorage` (у
    той акаунт, від імені якого йшов запит; логотип у знімку не змінюється), а
    після `POST /ngo/logo`
    знімок отримує нове посилання на логотип; при помилці сховище не
    змінюється. Після змін у галереї список із сервера
    отримується заново з першої сторінки.
  - **Галерея** (`admin-panel/images-gallery`) — зображення 8:10 заввишки
    200px в один рядок із прокруткою по X; на краю, за яким ще є зображення,
    градієнт у колір тла. Кнопка видалення зʼявляється при наведенні (на
    пристроях без наведення завжди видна), плитка додавання стоїть останньою.
    Коли її не видно, на правому краї рядка зʼявляється маленька кнопка «+»
    (як «Розгорнути» бічного меню, віддзеркалена). Додавання відкриває вибір
    файлу (PNG, WebP, JPEG, JPG, GIF, як на сервері та як для аватара).
    - **Отримання списку.** При відкритті
      `GET /api/v1/loginpageimages?PageNumber=1&PageSize=20` (потрібне право
      `ViewLoginPageImages`; без нього запиту нема). Зображень може бути
      тисячі, тому далі підвантажується по одній сторінці, коли прокрутка
      наближається до кінця рядка (менше ~400px), а в кінці крутиться
      прелоадер; якщо рядок не заповнює вікно, сторінки добираються самі.
      Після помилки сторінки автоматично не повторюємо, а повторюємо, коли
      користувач знову докрутить до кінця. Немає зображень і немає права
      додавати — замість плитки блок «Наразі відсутні зображення для
      сторінки входу»; з правом додавати лишається плитка з плюсом.
    - **Три списки.** Зміни користувача лежать у трьох списках і на сервер
      йдуть лише за «Зберегти»: (1) зображення з системи; (2) зображення з
      системи, видалені користувачем (переносяться сюди з першого);
      (3) файли, додані користувачем. Видалення доданого файлу просто
      прибирає його з третього списку. Видалені не зʼявляються повторно,
      навіть якщо сервер віддасть їх на наступній сторінці. На час
      збереження додавання й видалення в галереї не приймаються.
  - **Обмеження:** скасувати
    видалення до збереження не можна (лише перезавантажити сторінку, що
    скидає всі незбережені зміни); підтвердження перед видаленням нема;
    запитів багато — по одному на кожне видалення й завантаження.
- **Колеги** (`/colleagues`). Шапка: заголовок і справа кнопки «Ролі»,
  «Додати» та пошук (на телефоні в кнопках лишаються іконки). Нижче таблиця
  колег (спільний `app-data-table`): колонки ПІБ (аватар, імʼя, займенники),
  Посада (плашки ролей колеги в рядок і під ними рядки «проєкт — роль» з
  кольоровою крапкою), Пошта й Телефон; наведений рядок
  виділяється акцентним кольором меню, в кінці рядків стоять три крапки, а в
  кінці рядка заголовків — «+». Колонки (`columns`) і рядки (`rows`) задаються
  кодом у `ColleaguesPage`, складні комірки — шаблони в її розмітці. Колеги
  приходять із `GET /api/v1/users` по 20: перша сторінка при відкритті вкладки,
  наступні підвантажуються при прокрутці до кінця таблиці (`ion-infinite-scroll`,
  поріг 200px; запит, що ще триває, не дублюється, колега, що вже є, вдруге не
  додається). Рядок будується з полів колеги (`UserSummary`): імʼя (`firstName`
  і `lastName` через пробіл), пошта, `phoneNumber`, `country`,
  `emergencyContact`, `pronouns`, `pronounCategory`, `avatarUrl`, `roles`.
  Телефон, країна, екстрений контакт, займенники з категорією, аватар і ролі
  читаються з відповіді, якщо сервер їх віддає (розширений список є не в усіх
  версіях API); інакше `toUserSummary` ставить `null` і порожній список, і таблиця
  показує запасні значення. Порожні імʼя, пошта й телефон та рядки «проєкт — роль»
  (два, зелена й синя крапки; проєктів сервер не віддає) — плейсхолдери з
  мовного файлу (`colleagues.sample.*`). Займенники: за категорією (1 —
  «Він/його», 2 — «Вона/її», 3 — «Вони/їх»; категорії з `PronounCategory`
  сервера), без категорії (варіант «Інше» в профілі) — власний текст
  `pronouns`, нема й його — прочерк (`common.empty`). Аватар — `app-avatar` з
  імʼям, прізвищем і назвою організації користувача (колір без зображення
  рахується так само, як у меню). Ролі колеги в колонці «Посада» — ті самі
  плашки (`app-role-pill`), що у вікні «Ролі», в рядок із проміжком 9px, з
  перенесенням на наступний рядок; без ролей плашок нема. Під таблицею показується «Завантажуємо колег…»,
  «Колег ще нема.» або причина помилки (`colleagues.list.error.*`) з кнопкою
  «Спробувати ще раз» (вже завантажені колеги лишаються, а прокрутка на час
  помилки вимкнена). Сортування: заголовок колонки — кнопка (`app-data-table`,
  подія `sortChange`, колонка має `orderBy` — що йде в `OrderBy` запиту). Клік:
  перший — від меншого до більшого (`SortOrder=asc`, іконка
  `caret-down-outline`), другий — навпаки (`desc`, `caret-up-outline`), третій
  скидає вибір (запит без `OrderBy` й `SortOrder`, знову `filter-outline`, що
  видно при наведенні). Вибраним лишається один заголовок (комірка виділена,
  `aria-sort`). Кожен клік очищає таблицю й питає `GET /api/v1/users` з першої
  сторінки; вибране сортування передається й у наступні сторінки при
  прокрутці, відповідь на запит попереднього сортування ігнорується. `OrderBy`
  колонок: «ПІБ» — `LastName`, «Посада» — порожній (запит без сортування),
  «Пошта» — `Email`, «Телефон» — `PhoneNumber`. Сервер приймає одну
  властивість `UserDto` (точний збіг без урахування регістру; невідомі,
  зокрема `PhoneNumber`, дають порядок за `Id`), тож прізвище, імʼя й по
  батькові разом передати не можна. Три крапки в кінці рядка відкривають
  спливаюче меню
  дій (`app-popover` із `colleagues/colleague-actions`), кнопки «Ролі» й
  «Додати» та кожна дія меню відкривають бічне вікно (`app-side-panel`).
  Зміст вікна поки є лише в «Ролей» і «Додати»; **для дій меню, самих дій,
  пошуку й «+» нічого не зроблено.** Що показується, залежить від прав (зі
  знімка акаунта; права без префікса `Permissions.`):

  | Що на сторінці                         | Коли показується                         |
  |----------------------------------------|------------------------------------------|
  | Вкладка в бічному меню й сама сторінка | є `ViewUser`                             |
  | Кнопка «Додати»                        | є `CreateUser`                           |
  | Три крапки в кінці рядків              | є хоча б один пункт меню дій             |
  | Кнопка «+» у заголовках таблиці        | є `ViewCustomFields`                     |

  Меню дій біля трьох крапок складається з пунктів, кожен із яких
  показується за своїм правом (права без префікса `Permissions.`); три крапки
  є, коли доступний хоча б один пункт, інакше комірка в кінці рядка лишається
  порожньою, щоб таблиця не зсувалась. Поки меню відкрите, рядок лишається
  виділеним. Для рядка самого користувача (`id` рядка збігається з `id`
  профілю, а поки його нема, зі `userId` знімка акаунта) меню має єдиний пункт
  «Налаштування профілю» (як у меню акаунтів, без прав, веде на `/settings`),
  решта пунктів не показується.

  | Пункт меню       | Коли показується                      |
  |------------------|---------------------------------------|
  | Змінити ролі     | є `AssignRoleToUser` або `ManageRole` |
  | Редагувати       | є `UpdateUser`                        |
  | Скинути пароль   | є `CanResetPassword`                  |
  | Вимкнути акаунт  | є `DisableUser`                       |
  | Ввімкнути акаунт | є `UpdateUser`                        |
  | Видалити         | є `DeleteUser`                        |

  Вікно «Ролі». Кнопка «Ролі» в шапці відкриває бічне вікно на списку: при
  **кожному** відкритті йде `GET /api/v1/roles` (`RolesService`, `core/roles`:
  сторінки по 100, поки сервер каже `hasNextPage`; збій будь-якої сторінки це
  збій усього запиту, щоб неповний список не видавався за повний; для читання
  потрібна лише авторизація, тож список бачать усі, хто бачить вкладку). Поки
  йде оновлення, лишається попередній список, а запит, що ще триває, не
  дублюється. Ролі показані тегами (`app-role-pill`, колір за назвою), є стани
  «Завантажуємо ролі…», «Ролей ще нема.» і помилка за причиною
  (`colleagues.rolesPanel.*`).

  Керування ролями вимагає `ManageRole`; без нього вікно має лише заголовок,
  хрестик і список. З правом: зверху зліва, на одній висоті з хрестиком,
  кнопка «Додати роль» (слот `sidePanelHeader` вікна), а по правому краю
  кожного рядка кнопки «Редагувати» (олівець) і «Видалити» (смітник)
  (`deleteRole(role)` — заглушка). «Додати роль» замінює
  список формою «Нова роль» (`app-role-form`), а кнопка в шапці стає «Назад»
  (список лишається без нового запиту): поля «Назва» (обовʼязкове),
  «Фемінітив» і «Множина» (до 256 символів, як на сервері) та кнопка
  «Додати», яка перевіряє назву й віддає дані (разом із правами вибраних
  груп) у `createRole(role)`. Над кнопкою стоять тумблери прав за таблицею
  «Назви прав» (спочатку всі вимкнені). Надати можна лише права, які є в
  самого користувача (з його профілю): тумблер групи доступний, коли є **всі**
  її права (для обʼєднаних груп перевірка за AND, `canGrantGroup`), інакше він
  вимкнений, рядок приглушений, а підказка пояснює причину. «Додати»
  відправляє роль (`RolesService.create`): `POST /api/v1/roles` з назвами
  (порожні — `null`), а далі для кожного права окремий
  `POST /api/v1/roles/{id}/claims/{право}` по черзі (так сервер задає права;
  невдача одного не зупиняє решту): права вибраних груп і права без
  налаштування `ViewNgo` та `ViewTableTemplate` (додаються до кожної ролі в
  будь-якому випадку; `CreateNgo` лише в першого користувача, його не
  додаємо). Поки йде відправка, кнопка вимкнена; успіх повертає до оновленого
  списку (якщо не всі права додалися, над списком попередження
  `colleagues.rolesPanel.noticePartial`), невдача створення лишає форму з
  помилкою за причиною (`colleagues.roleForm.saveError.*`). «Редагувати» питає
  роль у сервера (`GET /api/v1/roles/{id}`,
  `RolesService.get`, відповідь має ще й `claims`) і замість списку показує ту
  саму форму, заповнену назвами ролі: заголовок «Редагування ролі», кнопка
  «Зберегти» відправляє зміни (`RolesService.update`): `PUT /api/v1/roles/{id}`
  з `{newName, feminitiveName, pluralName}` (порожні необовʼязкові — `null`), а
  далі по черзі окремими запитами `POST` (додати) і `DELETE` (прибрати) на
  `/api/v1/roles/{id}/claims/{право}` за різницею з початковими `claims` ролі
  (`diffClaims`). Зачіпаються лише групи, які користувач може надати (є всі
  права групи, AND): увімкнена додає права, яких у ролі нема, вимкнена
  прибирає свої права (так виправляється й часткова група); недоступні групи й
  права поза групами не чіпаються; права без налаштування `ViewNgo` та
  `ViewTableTemplate` додаються, якщо їх нема. Невдача окремого права не
  зупиняє решту. Поки йде відправка, кнопка вимкнена; успіх повертає до
  оновленого списку (якщо якусь зміну прав не вдалося застосувати, над списком
  попередження `colleagues.rolesPanel.noticePartialUpdate`), невдача
  збереження назв лишає форму з помилкою (`colleagues.roleForm.updateError.*`),
  права не чіпаються. Тумблери прав заповнюються з `claims` ролі: група ввімкнена, коли в ролі є всі її права;
  часткова (є лише частина прав) лишається вимкненою й позначається іконкою
  `alert-circle-outline` із підказкою при наведенні чи фокусі: проблема з
  роллю, яку виправить оновлення ролі (`colleagues.roleForm.partialTitle`,

## Назви прав

Таблиця нижче — основа для тумблерів прав у формі створення ролі
(`core/roles/role-permissions.ts`, назви в `colleagues.roleForm.permissions.*`).
Кілька кодів в одній групі відповідають одному тумблеру, разом їх 10; щоб
надати групу, користувач має мати всі її коди (AND).
Нижня секція — права, які в ролі не вибирають, бо вони вже є у всіх чи
видаються автоматично. Коди — без префікса `Permissions.`.

----------------------+-----------------------------------------------------------------------------

DeleteUser            |
----------------------+-----------------------------------------------------------------------------
CanResetPassword      | Скидання паролів колег
----------------------+-----------------------------------------------------------------------------
ManageRole            | Керування ролями

----------------------+-----------------------------------------------------------------------------

## Обмеження, що випливають зі способу постачання

**Статична збірка.** Клієнт — односторінковий застосунок; результат `ng build`
віддає nginx. Образ не містить Node.js. Це знімає потребу в серверному рантаймі
на боці адміністратора інсталяції.

**Порт.** Контейнер слухає порт 8080 (non-root nginx). Локально його
публікує `compose.yaml` на `localhost:8080`; на сервері перед ним стоятиме
зворотний проксі з HTTPS.

**Кешування.** Файли з хешем у назві (`main-*.js`, `chunk-*.js`,
`styles-*.css`, `media/`) кешуються на рік, усе інше, зокрема `index.html`
і `assets/i18n/*.json`, браузер перевіряє щоразу. Тому нові переклади й
зображення в `assets/` підхоплюються без скидання кешу.

**Конфігурація під час виконання.** Один образ працює на всіх інсталяціях, тому
нічого специфічного для середовища не вбудовується у збірку, зокрема в
`environments/`. Адресу API клієнт визначає в рантаймі через
`ConnectionService`: надана користувачем адреса з `localStorage` або домен, з
якого відкрито сторінку (порт 5065 за замовчуванням). Під час розробки `ng
serve` додатково проксує `/api` на `http://localhost:5065`.

**Без серверної логіки в клієнті.** Автентифікація, валідація та бізнес-правила
реалізовані в `apps/api`. Клієнт не проксує та не агрегує виклики API. Перевірки
у формах (наприклад, складність пароля) виконуються лише для швидкого відгуку
користувачу.

**Токени.** Обидва токени кожного акаунта зберігаються в його записі в
`localStorage`. Це зручно для довільної адреси сервера (куки з іншим сайтом
блокуються), але означає, що XSS у сторінці може прочитати токени.

**Локалізація.** Інтерфейс розрахований на українську, англійську,
кримськотатарську й білоруську мови; мова визначається з мови пристрою при
першому відкритті, а для ввійшовшого користувача — з `preferredLanguage` його
профілю. Тексти зберігаються окремо від компонентів (`assets/i18n/*.json`) з
першого коміту, але поки заповнено лише українські.

## Мобільні застосунки

Ionic дає можливість зібрати клієнт як мобільний застосунок через Capacitor.
Пакети `@capacitor/*` уже є в `package.json` (частина шаблону), але
`capacitor.config` і нативні проєкти відсутні. Рішення про мобільний застосунок
не ухвалене. Наслідок для архітектури: мобільний застосунок стає другим
споживачем API з власним циклом випуску, що вимагає політики сумісності API,
якої зараз немає.
