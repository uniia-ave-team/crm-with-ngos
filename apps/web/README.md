# Вебклієнт

Клієнт на Ionic Angular. Каталог самодостатній: `package.json` і
`package-lock.json` розташовуються тут, а не в корені репозиторію. Спільного
workspace з `apps/api` немає. Пакет називається `Yavir`.

Застосунок має робочу оболонку (бокове меню, девʼять сторінок, локалізація),
сторінку входу, яка вже працює з `apps/api`, сторінку запрошення колеги,
сторінку налаштувань профілю й сторінку «Адмін».
Вхід перевіряє підключення, веде через первинне налаштування системи
(адміністратор, організація), виконує вхід і підтримує сесію. Сесія — це
збережені в `localStorage` акаунти (див. «Акаунти»). Користувач може мати кілька
акаунтів: додає їх кнопкою «+» в меню акаунта й перемикається клацанням по
плитці. «Календар» поки прихований у меню (`.planned`), «Планер» — проєкти, їхні дошки, завдання
й коментарі, «База знань» показує зміст на зразкових даних; «Колеги» показує таблицю колег із
сервера, ролі й запрошення.

## Стек

| Частина          | Версія / інструмент                                              |
|------------------|------------------------------------------------------------------|
| Фреймворк        | Angular 22, standalone-компоненти (без NgModule)                 |
| UI               | Ionic Framework 9 (`@ionic/angular`); іконки — Lucide і Material Symbols |
| Локалізація      | `@ngx-translate/core` 18 (standalone API, без `TranslateModule`) |
| Шрифт            | e-Ukraine (Regular/Light/Medium/Bold), локально в `assets/fonts` |
| Мова             | TypeScript 6                                                     |
| Збірка           | Angular CLI 22, builder `@angular/build:application`             |
| Тести            | Vitest 4 + jsdom через `ng test`                                 |
| Лінтер           | ESLint 10, angular-eslint, typescript-eslint                     |
| Менеджер пакетів | npm                                                              |

## Вимоги

Node.js **22.22.3 або новіший** (також підходять 24.15+ і 26+); рекомендовано 24, як у
`.nvmrc` і CI.

## Команди

Усі команди виконуються в `apps/web`.

```bash
npm install                        # встановити залежності
npm start                          # ng serve, http://localhost:4200
npm run build                      # production-збірка у www/
npm run watch                      # збірка з перезбиранням (development)
npm test                           # Vitest у режимі спостереження
npm run test:ci                    # Vitest, один прогін (для CI)
npm run lint                       # ESLint для src/**/*.ts і src/**/*.html
npm run lint:fix                   # ESLint з автовиправленням
npm run generate                   # generate:api + generate:languages
npm run generate:api               # клієнт API з openapi.json
npm run generate:languages         # список мов із src/assets/i18n/*.json
npm run check:icons                # усі іконки з коду є в core/icons.ts
```

З кореня репозиторію те саме доступне через `just`: `just web`,
`just test-web`, `just web-ci`.

`npm start`, `npm run build`, тести й лінт спершу генерують потрібне: клієнт
API з `packages/api-contract/openapi.json` у `src/app/api/generated` і список мов
`src/app/core/i18n/languages.generated.ts` зі `scripts/generate-languages.mjs`
(npm-хуки `prestart`, `prebuild`, `pretest`, `pretest:ci`, `prelint`,
`prelint:fix`). Обидва ігноруються git. `prelint` і `prelint:fix` після
генерації ще запускають `check:icons` (див. «Іконки»).

`ng build` кладе результат у `www/`, а не в `dist/`. Саме звідти `Dockerfile`
копіює статику для nginx. Каталог `www/` ігнорується git.

Production-образ локально: `just up` з кореня репозиторію, потім
<http://localhost:8080>. API, яке піднімає `just up`, слухає
`http://localhost:5065` і приймає запити й з `ng serve` (`:4200`), тож для
роботи з реальними даними .NET не потрібен: `just up`, потім `npm start`.

Бюджети production-збірки: початковий бандл — попередження від 2 МБ, помилка
від 5 МБ; стилі компонента — 4 і 8 КБ.

## Поточний стан

Створено:

- **Каркас і навігація.** `AppComponent` — оболонка застосунку: бокова панель
  (`core/layout/primary-nav`, десктопна колонка / мобільні верхня й нижня
  панелі) і друга контекстна панель (`core/layout/secondary-panel`) для
  сторінок «База знань», «Планер» і «Налаштування». Сторінки без бічного меню взагалі
  (наразі — `/login`, `/join`, `/reset-password` і `/relogin`) позначаються
  `data: { layout: 'none' }` у маршруті й читаються через `LayoutService.hideShell`; місце
  під мобільні панелі резервується лише всередині оболонки. Поки йде пошук чинного
  акаунта (старт застосунку, перехід на захищену сторінку), поверх усього
  показується повноекранний прелоадер (`shared/preloader`).
- **Одинадцять сторінок:** `start` (стартова, див. нижче), `calendar` (порожня заглушка з
  перекладеним заголовком), `planner` (і `planner/projects/:id` — планер проєкту, див. нижче),
  `knowledge-base` (див. нижче), `colleagues`,
  `admin-panel`, `settings` (див. нижче), `login`, `join`, `reset-password` і `relogin` — сторінки
  без бічного меню. На стартовій адресі `/` відбувається переадресація на `/login`. Пункти
  основного меню: Календар, Планер, База знань, Колеги і Адмін (іконка `hammer-outline`, адреса
  `/admin-panel`); лого веде на `/start`. «Планер» показується лише тим, у кого є
  `Permissions.ViewProject`, «Колеги» — лише тим, у кого є `Permissions.ViewUser`. «Адмін»
  показується лише тим, у кого є **хоча б одне** з прав: `Permissions.UpdateNgo`,
  `Permissions.CreateLoginPageImages`, `Permissions.DeleteLoginPageImages` (права активного
  акаунта зі знімка в `localStorage`; поки їх не отримано, пункту нема). На телефонах шириною до
  400px підписи нижнього меню мають 10px і не переносяться, бо пʼять пунктів
  ділять ширину екрана. Кнопка «Зоря» (іконка `zoria.svg`) у бічній і
  мобільній верхній панелях запланована й поки схована (`.planned`); до низу рейла тоді
  притискається сам блок акаунта.
- **Сторінка входу** веде користувача через підключення, первинне
  налаштування системи й вхід. Якщо в `localStorage` є збережені акаунти,
  спершу шукається чинний (див. «Акаунти»): знайшовся — одразу перехід на
  `REDIRECT_URL` (зараз `/start`), форми не показуються, а поки пошук
  триває, видно «Перевіряємо підключення…»; не знайшовся, але акаунти
  лишились — перехід на `/relogin`. Ionic тримає сторінку в стеку, тож
  при поверненні на неї (наприклад, коли на `/relogin` видалили останній
  акаунт) пошук запускається знову. Якщо акаунтів нема взагалі,
  перевіряється підключення: немає — форма адреси сервера; є —
  запитується `GET /api/v1/system/status`. Далі за статусом і наявністю
  активного акаунта (він зʼявляється, коли користувач щойно ввійшов або
  зареєстрував адміністратора на цій сторінці). Рядки перевіряються зверху
  вниз; `—` означає «неважливо»:

  | `isSetupComplete` | `hasAdmin` | `hasNgo` | Активний акаунт | Результат                       |
  |-------------------|------------|----------|-----------------|---------------------------------|
  | `true`            | —          | —        | немає           | форма входу                     |
  | `true`            | —          | —        | є               | перехід на `REDIRECT_URL`       |
  | `false`           | `false`    | —        | —               | форма реєстрації адміністратора |
  | `false`           | `true`     | `false`  | є               | форма створення ГО              |
  | `false`           | `true`     | `false`  | немає           | форма входу                     |
  | `false`           | `true`     | `true`   | —               | помилка налаштування системи    |

  Якщо статус отримати не вдалося, показується форма входу. Помилка
  налаштування системи має текст «Сталася помилка при налаштуванні системи.»

  - **Форма входу** (зображення зліва, форма справа; на вузьких екранах лише
    форма): пошта й пароль. `POST /api/v1/auth/login`, вхід зберігається
    як акаунт (адреса сервера, токени, пошта), запитується статус системи:
    немає ГО — форма створення ГО, є — перехід на `REDIRECT_URL`. Лого Явору —
    мобільне лого меню (за мовою й темою), лого Унії — `Uniia.svg` для
    української, кримськотатарської й білоруської, `Uniia_en.svg` для решти
    (вибір у `core/i18n/logos.ts`, як і для лого «Явір»: нова мова отримує
    `Uniia_en.svg`);
    лого партнерів і зображення — зі світлими (`assets/logos`) і білими
    (`assets/logos_white`) варіантами для темної теми. Зображення збоку форми —
    випадкове з тих, що завантажені в системі:
    `GET /api/v1/loginpageimages/random` (публічний запит, токен не потрібен),
    робиться один раз на сервер, коли показано саму форму входу. Відповідь, що
    прийшла вже після зміни адреси, відкидається. Поки запит іде,
    а також коли зображень нема (`404`), сервер не відповів чи зображення не
    завантажилось, показується стандартне `assets/login_image.jpg`.
  - **Форма адміністратора:** пошта, прізвище, імʼя, по батькові (необовʼязкове,
    у запит іде `null`, якщо порожнє), пароль і його повтор. Пошта перевіряється
    так само, як на сервері (`shared/email`: один `@`, не на краях, без пробілів,
    до 256 символів);
    `POST /api/v1/users`, потім одразу `POST /api/v1/auth/login` з тими самими
    даними. Пароль має відповідати умовам сервера (див. «Умови до пароля»
    нижче); умови виведено списком під полем пароля й відмічаються під час
    введення, під повтором відмічається збіг паролів.
  - **Форма ГО:** назва й логотип (поле перетягування з превʼю та круглою
    кнопкою видалення). `POST /api/v1/ngo` (лише назва); якщо
    обрано логотип, після цього першого запиту йде `POST /api/v1/ngo/logo`
    (`multipart/form-data`, поле `file`) із самим зображенням, потім перехід
    на `REDIRECT_URL`. Організація створюється один раз: якщо логотип не
    завантажився, показується помилка, назва стає лише для читання, а
    повторне «Продовжити» повторює тільки завантаження логотипа (або, якщо
    файл прибрали, одразу веде далі).
  - **Кнопка «змінити адресу сервера»** (кругла, з іконкою сервера, праворуч
    угорі кожної форми, крім кроку адреси): спершу один запит `GET /health`
    на поточний сервер, потім повне очищення `localStorage` і форм та
    повернення на крок адреси; якщо сервер був здоровий, його адресу
    підставлено в поле. Кнопка скидає все, що збережено в браузері для
    застосунку: адресу сервера, мову, акаунт, який зараз налаштовується
    (наприклад, щойно створеного адміністратора, коли відкрито форму ГО), і
    застарілі акаунти. Інших акаунтів на цій сторінці бути не може: чинний
    перекинув би на `REDIRECT_URL`, а застарілі чи недоступні — на `/relogin`.
  - **Помилки:** валідація форм — до будь-якого запиту. Помилки полів
    показуються під ними, а відповіді сервера (і помилка прізвища у формі
    адміністратора) — окремим блоком над формою; у формі входу — блоком над її
    полями.
  - **Форма входу — спільна** (`app-sign-in-form`, `core/auth/sign-in-form`): пошта,
    пароль, «Ввійти», «Забули пароль?» (поки без дії) і, якщо задано `withServer`,
    поле адреси сервера. Її використовують ця сторінка (без поля адреси: сервер уже
    визначено), сторінка `/relogin` і вікно входу з меню акаунтів (обидва з полем).
    З полем адреси сервер перевіряється після кожної зміни (пауза 0,5 с, перша
    перевірка одразу; `GET /health`): недоступний чи не схожий на адресу —
    повідомлення під полем, «Ввійти» вимкнена; `serverChange` віддає origin
    здорового сервера або `null`. Вхід — `POST /api/v1/auth/login` на цьому сервері;
    якщо `accountId` вказує на збережений акаунт із тією самою поштою (без
    урахування регістру), він перезаписується, інакше додається новий; акаунт стає
    активним. Далі форма викликає `afterSignIn` того, хто її показує, і до його
    завершення лишається зайнятою. Помилки пошти й пароля — під полями, відповідь
    сервера — блоком над полями; там само показується `error` — помилка того, хто
    показує форму.
  - **Стилі форм входу й реєстрації — спільні** (`src/theme/auth-form.scss`, глобальні
    класи `auth-*`): блок помилки, підпис, поле, помилка під полем, головна кнопка
    й другорядне посилання. Їх використовують `login`, `join`, `relogin` і вікно
    входу; у компонентах лишається тільки розкладка. Поле має селектор
    `ion-input.auth-input.input-fill-outline`: Ionic додає свої стилі поля після
    глобальних, і самого класу за однакової ваги замало.
  - Усім полям і кнопкам задано `tabindex`, бо в Safari без нього не працює
    табуляція.
- **Сторінка запрошення** (`/join?token=…`) — куди веде посилання з вікна «Додати
  колегу». Без стражів і без бічного меню. Працює із сервером за доменом сторінки
  (`ConnectionService.pageServerUrl`), а не активного акаунта: колега може вже мати
  акаунт деінде, а запрошення — на цей сервер. Кроки:
  1. `GET <сервер>/health`. Сервера нема — червоний блок «Ми не можемо знайти
     сервер. Спробуйте з локальної мережі своєї ГО або зверніться до
     адміністратора.» і посилання «На головну» (на `/login`);
  2. `GET /api/v1/invitations/validate?token=…` (без токена в посиланні запиту нема).
     Сервер відхилив токен (прострочений чи зіпсований; `400`) —
     блок «Надане посилання неактивне. Зверніться до адміністратора.» з тим самим
     посиланням «На головну». Акаунт із поштою запрошення вже є (`409`, зокрема
     запрошення вже прийняли) — блок «Акаунт із поштою цього запрошення вже існує.
     Увійдіть у нього.» з посиланням «Увійти» (на `/login`). Інша невдача (сервер не
     відповів, помилка сервера, відповідь без пошти) про токен нічого не каже — блок
     «Не вдалося перевірити запрошення…» з кнопкою «Спробувати ще раз», що повторює
     обидві перевірки;
  3. форма: пошта з відповіді (неактивне поле), прізвище, імʼя, по батькові
     (необовʼязкове, порожнє йде в запит як `null`), пароль і його повтор
     (`app-password-fields`, правила як у формі адміністратора; помилка прізвища,
     як там, — блоком над формою). Стилі — спільні класи `auth-*`
     (`src/theme/auth-form.scss`), розкладка — як на `/login`;
  4. «Зареєструватися» — `POST /api/v1/invitations/accept`. У відповіді пара
     токенів: `AuthService.adoptTokens` додає акаунт як активний, далі перехід на
     `REDIRECT_URL`. Помилка — червоний блок над формою (`join.saveError.*`; `409` —
     «Акаунт із цією поштою вже існує…»),
     форму можна надіслати ще раз. Відповідь на перевірку для старого токена
     (посилання змінили, поки йшов запит) ігнорується. Тексти — `join.*`.
- **Сторінка нового пароля** (`/reset-password#token=…`) — куди веде посилання з вікна «Посилання
  для скидання пароля створено». Без стражів і без бічного меню; сервер — за доменом сторінки
  (`ConnectionService.pageServerUrl`), як на `/join`. Спершу — «Перевіряємо посилання…»: токен
  перевіряється (`GET /api/v1/users/reset-password/validate`, `UsersService.validatePasswordReset`,
  без авторизації). Сервер відхилив токен (400: строк минув, ним уже скористалися, пошкоджений) чи
  токена нема — «Посилання неактивне…» з «Назад» на `/relogin`; інша невдача — «Не вдалося
  перевірити посилання…» з «Спробувати ще раз». Інакше — картка «Скидання паролю»: пошта акаунта,
  пароль якого скидають (неактивне поле), «Пароль» і «Повторити пароль» (`app-password-fields`,
  умови сервера за доменом сторінки, щонайбільше 128 символів), «Відправити» й під нею «Скасувати»
  (на `/relogin`). «Відправити» —
  `POST /api/v1/users/reset-password` з `{token, newPassword}` (`UsersService.resetPassword`, без
  авторизації); успіх — перехід на `/relogin` із зеленою плашкою вгорі «Пароль змінено. Увійдіть з
  новим паролем.» (`SuccessNoticeService`, `core/notice`: плашка в корені застосунку, тож переживає
  перехід; зникає за 6 с або хрестиком). Невдача замінює форму червоним блоком за причиною
  (`resetPassword.failure.*`: `400` — сервер не прийняв, можливо, посиланням уже скористалися; `401`
  — посилання неактивне; інше) з кнопкою «Назад» на `/relogin`. Без збережених акаунтів `/relogin`
  веде далі на `/login`.
  Стилі картки — з `join.page.scss`. Тексти — `resetPassword.*`.
- **Сторінка повторного входу** (`/relogin`) — куди веде відсутність доступних
  акаунтів, коли збережені ще є. Без стражів і без бічного меню. Вибір акаунта у
  стилі Google: зображення зліва (стандартне `assets/login_image.jpg`), як на
  `/login`, справа лого «Явір», заголовок, список збережених акаунтів (у порядку
  додавання, також застарілих і недоступних) і кнопка «Додати акаунт». Рядок —
  аватар (`app-account-avatar`: значок стану, логотип ГО) і підпис: у першому рядку
  «ПІБ — Назва ГО», у другому (якщо треба) «Відсутнє підключення до сервера» чи
  «Сеанс закінчився» (ті самі тексти, що в підказці плитки меню; без імені й ГО —
  «Акаунт»). Кнопка додавання — той самий вигляд і підпис, що в меню акаунтів. Якщо
  акаунтів нема взагалі (також коли вони зникнуть, поки сторінка відкрита),
  переадресація на `/login`.
  - **При відкритті:** для кожного недоступного, але не застарілого акаунта
    пробується обмін токенів (`AuthService.refreshStored`): вдалося — токени нові,
    `unavailable` знято; токени відхилено — акаунт `outdated`; сервер мовчить —
    без змін.
  - **Вибір у списку:** доступний або недоступний, але не застарілий акаунт —
    `AccountRestoreService.activate`: успіх — він активний і відкривається
    `REDIRECT_URL`, помилка — форма з його даними. Застарілий (з `unavailable` чи
    без) — одразу форма. «Додати акаунт» — форма для нового. Поки йде
    перемикання, повторні клацання ігноруються.
  - **Форма** (`relogin/relogin-form`, на місці списку; зображення зліва
    лишається): «Назад» — до списку; заголовок «Ввійти в акаунт» і смітник на одному
    рядку (для нового акаунта смітника нема): смітник видаляє дані акаунта з
    памʼяті й повертає до списку (не лишилось акаунтів — `/login`). Під ними —
    спільна форма входу (`app-sign-in-form`, див. «Сторінка входу») з полем адреси:
    адреса сервера — акаунта або домену сторінки (для нового), пошта — акаунта або
    порожня. Коли форма повідомляє про здоровий сервер, з нього береться випадкове
    зображення (`random(server)`), інакше — стандартне. Після входу підключення
    перевіряється на сервері акаунта, і відкривається `REDIRECT_URL`.
- **`ConnectionService`** (`core/connection`) — визначає, до якого сервера
  підключатися, і перевіряє його:
  - адреса сервера: надана користувачем (зберігається в памʼяті, а після
    входу — у записі акаунта) має пріоритет і без запасного варіанта; якщо її
    нема — домен, з якого відкрито сторінку. Порт за замовчуванням — 5065;
  - перевірка `GET <сервер>/health` (таймаут 5 с) дає стан `healthy`,
    `unhealthy` або `unreachable` (невдача пишеться в консоль); нова перевірка
    скасовує попередню, а той, хто на неї чекав, отримує результат нової;
  - `loadSystemStatus()` запитує `GET <сервер>/api/v1/system/status`; відповідь не за
    контрактом `SystemStatusDto` (три булеві поля, `version` — рядок, `notice` — `null`
    чи оголошення з `message`, `startsAt`, `endsAt`) вважається невдалою. Оголошення
    про технічні роботи показує `MaintenanceNoticeService` (`core/maintenance`):
    жовта плашка вгорі на всіх сторінках, поки роботи не скінчились («Заплановано…»
    чи «Тривають…», дати мовою інтерфейсу); закрита — до перезавантаження, нове
    оголошення — знову. Статус він запитує при кожній новій перевірці підключення,
    крім пошуку акаунта при старті;
  - `pageServerUrl` — сервер за доменом сторінки (`<протокол>://<домен>:5065`)
    незалежно від акаунтів і наданої адреси (для `/join`); `probeApi(server?)` —
    одноразова перевірка `GET /health` поточного чи заданого сервера, що не чіпає
    стан сервісу; `parseServerAddress()` розбирає введену адресу в URL;
  - `idn.ts` — кириличні домени (зона `.укр`). У посиланні браузер тримає такий
    домен латиницею (`приклад.укр` → `xn--80aikifvh.xn--j1amh`), і запити йдуть
    саме туди; `hostnameToUnicode()` і `serverAddressToUnicode()` розкодовують його
    назад — для `id` акаунта й для показу адреси в полях вводу та повідомленнях.
- **Стражі сторінок** (`core/auth`, `core/connection`). Усі сторінки, крім
  `/login`, `/join`, `/reset-password` і `/relogin`, проходять `authGuard`, а потім
  `connectionGuard`. Маршрути мають
  `runGuardsAndResolvers: 'always'`, тому стражі спрацьовують при **кожній**
  зміні сторінки (також між вкладками налаштувань), а не лише коли маршрут
  активується вперше. Обидва стражі й `runGuardsAndResolvers: 'always'` зібрано в
  одну константу `SIGNED_IN` (`app.routes.ts`): нова сторінка бере її цілком, тож
  забути стража не вийде. Невідома адреса (`**`) веде на `/login`, а звідти пошук
  акаунта відкриває першу сторінку чи форму входу. Права користувача (`permissions`) не приходять у
  відповіді `/users/me`: після кожного його успіху `CurrentUserService`
  окремо запитує `GET /users/me/permissions` і записує їх у знімок акаунта;
  інтерфейс (меню, сторінка «Адмін») читає їх звідти.
  - `authGuard`, коли поточний акаунт уже підтверджено в цій сесії сторінки
    (профіль у памʼяті): пускає одразу, а у фоні перепитує профіль —
    `GET /users/me`, разом із ним права й назву ГО (див. `CurrentUserService`).
    Так зміни в БД (дані профілю, права, назва й логотип ГО) потрапляють в
    інтерфейс без перезавантаження. Запит сторінку не блокує: невдача лишає
    попередні дані, недійсні токени обробляє `authInterceptor`: оновлює їх, а
    якщо не вдалося — `AuthService.expireSession` (акаунт лишається в памʼяті з
    позначкою `outdated` чи `unavailable`, активного більше нема), а на
    `/relogin` веде `SessionService`. Інша невдача — привід перевірити сервер
    (`GET /health`): не відповідає — акаунт стає `unavailable` і так само веде на
    `/relogin`; відповідає (наприклад, профіль не за контрактом) — лишаємось на сторінці.
  - Коли профілю ще нема (перше відкриття, перезавантаження, одразу після
    входу): шукає чинний акаунт серед збережених так само, як сторінка входу,
    і перший знайдений стає поточним (запит `/users/me` робить сам пошук, тож
    другого немає; одразу після нього, як і на кожному шляху, йде
    `GET /users/me/permissions`: права пишуться в запис акаунта, і меню «Адмін»
    будується з них без перезавантаження). Результат пошуку: `restored` —
    пускає; інакше доступного акаунта нема: переадресація на `/relogin`,
    якщо збережені акаунти є, і на `/login`, якщо їх нема взагалі.
  - `connectionGuard` додатково вимагає, щоб API за поточною адресою
    відповідав. Інакше активний акаунт позначається недоступним, і користувач
    потрапляє на `/relogin` (без збережених акаунтів — на `/login`; на практиці
    туди раніше веде `authGuard`). Невдачу, відому від давнішої перевірки, страж
    спершу перевіряє ще раз.
  - `requireAnyPermission([...])` (`core/auth/permission.guard.ts`) стоїть
    третім на маршрутах `/admin-panel` (`ADMIN_PANEL_PERMISSIONS`), `/planner`
    (`PLANNER_PERMISSIONS`, тобто `ViewProject`; пункт меню ховається так само),
    `/colleagues` (`COLLEAGUES_PERMISSIONS`, тобто `ViewUser`) і `/knowledge-base`
    (`KNOWLEDGE_BASE_PERMISSIONS`, тобто `ViewCustomTable`; пункт меню ховається так
    само), а також на `/knowledge-base/templates` (`TABLE_TEMPLATES_PERMISSIONS`, тобто
    `ViewTableTemplate`; так само ховається кнопка менеджера шаблонів): пускає лише
    того, у кого є **хоча б одне** з перелічених прав, інакше переадресація на
    `REDIRECT_URL` (стартова сторінка: вона веде на першу доступну). Свіжі права бере
    `freshPermissions` (там само; її ж використовує стартова сторінка). Стражі маршруту
    стартують одночасно, тож цей сам чекає входу (пошук акаунта спільний з
    `authGuard`; відмову входу оформлює `authGuard`, а цей лише не пускає).
    Далі вирішують свіжі права: профіль перепитується (`GET /users/me`) і
    страж чекає, поки `/users/me/permissions` потраплять у знімок акаунта,
    тож права, відкликані в БД, діють одразу. Якщо оновити не вдалося (сервер
    не відповів), лишаються збережені права. Цим стражем сторінка
    відкривається із затримкою на два запити (на відміну від решти, де запит
    іде у фоні).
- **Акаунти** (`core/accounts`):
  - `AccountsService` — сховище акаунтів у `localStorage`: запис на акаунт
    (`yavir.account.<id>`) та індекс (`yavir.accounts`). Активний акаунт у кожної
    вкладки свій: вказівник (`yavir.activeAccount`) лежить у `sessionStorage`, тож
    переживає перезавантаження сторінки й не залежить від інших вкладок. Нова
    вкладка починає з акаунта вкладки, яку користувач бачив останньою
    (`yavir.lastActiveAccount` у `localStorage`; підказкою стає лише акаунт, чий запис уже є
    в сховищі). Запис містить адресу сервера, токени, пошту,
    ознаку користувача (`identity`), знімок профілю (прізвище, імʼя, по батькові, аватар,
    назва та посилання на логотип ГО, їхні мініатюри `avatarThumb` і
    `ngoLogoThumb`), права користувача (`permissions` —
    список рядків із `GET /users/me/permissions`, оновлюється разом із
    профілем при кожній зміні сторінки), ролі користувача (`roles` — список
    `{id, name}` з поля `roles` відповіді `GET /users/me`, оновлюється разом
    із профілем; елементи без рядкових `id` й `name` і не-масив у сховищі
    читаються як порожній список), незалежні прапорці `outdated` (сервер
    відхилив токени) і `unavailable` (сервер не відповів) та час отримання
    токенів (`tokensIssuedAt`). `id` акаунта — домен сервера лише літерами
    (латинськими й українськими; кириличний домен спершу розкодовується з `xn--…`)
    та хеш сервера й користувача (наприклад, `localhost-3ee638bc`); при збігу хешу
    додається суфікс `-2`, `-3`. Зміни самих акаунтів в інших вкладках
    підхоплюються через подію `storage`: акаунт, з якого вийшли там, зникає й тут;
    акаунт, який там став `outdated`, перестає бути активним і тут. `update(id, patch)`
    перед записом підхоплює зі сховища токени, які встигла оновити інша вкладка.
    Запис зі сховища перевіряється по полях: поле не того типу стає значенням за
    замовчуванням, а запис без `id`, сервера чи токенів видаляється і з індексу, і
    зі сховища. Якщо браузер не дає читати сховище (заблоковано дані сайтів),
    акаунти живуть лише в памʼяті: працювати можна, доки вкладку не закрили й не
    перезавантажили. Якщо сховище читається, але не пишеться (переповнене), вхід
    не додає акаунта: `AuthService.adoptTokens` перевіряє запис (`isStored`), а не
    записавши, повертає памʼять до сховища, лишає активним попередній акаунт,
    відкликає щойно видані токени й дає `storageFull` — форми входу (`/login`,
    `/relogin`, «Додати акаунт»), реєстрація адміністратора й `/join` показують про
    це помилку. Якщо запис не вдається під час роботи (нові токени, мініатюри,
    вихід), вмикається `storageFull`, і застосунок показує спливаюче попередження
    (`ion-toast`, `common.storageFull`), поки його не закриють; невдалий вхід його
    вимикає — там помилка у формі. `add(input, replaceId?)` додає акаунт і робить його
    активним; той самий сервер і користувач — той самий акаунт, його токени
    оновлюються. `replaceId` — ключ акаунта, який перезаписується (сервер,
    користувач, токени) без створення нового: `id`, порядок і дата додавання
    лишаються; знімок профілю лишається, лише якщо це той самий користувач на
    тому ж сервері; інший запис цього користувача на цьому сервері видаляється.
    `markOutdated(id)` позначає акаунт `outdated` (і знімає `unavailable`),
    `markUnavailable(id)` — `unavailable`, `remove(id)` видаляє. Якщо такий
    акаунт був активним, активного більше нема: інший сам не підхоплюється.
    Памʼять не очищається (це робить лише «змінити адресу сервера» на `/login`;
    вихід видаляє лише активний акаунт). `switching` — прапорець пошуку чинного
    акаунта чи перемикання на інший (`setSwitching`): активним на мить стають
    акаунти, які лише перевіряються; на нього зважають профіль, сесія, меню й
    прелоадер;
  - `account-avatar` (`app-account-avatar`) — аватар акаунта зі значками: стан
    ліворуч унизу, логотип ГО праворуч унизу, обидва з контуром за альфа-каналом;
    розмір — `--avatar-size`. Використовують меню акаунтів і сторінка `/relogin`.
    Поруч `account-tile.ts`: дані плитки зі знімка акаунта й підпис «ПІБ — Назва
    ГО» зі станом;
  - `AccountRestoreService` — пошук чинного акаунта. Перший прохід — доступні
    акаунти (не `outdated`, не `unavailable`), активний першим; перший, що
    пройшов `/health`, токени (за потреби оновлюються) і `GET /users/me`, стає
    активним. Не пройшов: токени відхилено — `outdated`, сервер мовчить —
    `unavailable`. Доступного не знайшлось — другий прохід: недоступні, які такими
    були ще до пошуку (щойно недоступні не повторюються), перевіряються знову,
    кожен із `/health` власного сервера; успішний стає активним, його
    `unavailable` знімається. Застарілі пропускаються. Не пройшов жоден —
    активного нема, акаунти й токени лишаються в памʼяті. `activate(id)`
    перемикає на акаунт (клацання по плитці): робить його активним і перевіряє так
    само (`/health`, токени, `/users/me`). Успіх — лишається активним, `outdated` і
    `unavailable` знімаються; ні — активним повертається попередній, а цей
    позначається: токени відхилено — `outdated`, сервер не відповів —
    `unavailable`; профіль попереднього підтягується знову. На цей час, як і під
    час пошуку, вмикається `AccountsService.switching`. Пошук і перемикання йдуть
    строго по одному (спільна черга): обидва по черзі роблять активними різні
    акаунти, тож разом перевіряли б чужі. Попрошений під час перемикання пошук
    (наприклад, стражем сторінки) почнеться після нього, і навпаки; `switching`
    увімкнено, поки в черзі є хоч одна дія. `signOut()` — вихід:
    забуває активний акаунт, відкликає його токен і запускає той самий пошук (див.
    «Вийти»).
- **Сесія й токени** (`core/auth`):
  - `AuthService` — вхід та токени активного акаунта (access і refresh лежать
    у його записі); обмін токенів (`POST /api/v1/auth/refresh-token`)
    потребує обох. Refresh-токен одноразовий, тому обмін іде в одному
    екземплярі: у межах вкладки — один спільний запит на акаунт, між вкладками —
    Web Lock; нову пару, записану іншою вкладкою, підхоплюють зі сховища (подія
    `storage`), а не стирають. `refresh(accountId?)` оновлює токени того акаунта,
    для якого його викликали (за замовчуванням активного), навіть якщо тим часом
    активним став інший. Відповідь входу чи оновлення без пари непорожніх токенів —
    помилка. Невдале оновлення (400/401) позначає акаунт `outdated`.
    `expireSession(accountId, failure)` завершує сесію акаунта, якому не вдалося
    оновити токени: акаунт лишається (`outdated` для відхилених токенів,
    `unavailable` для мовчазного сервера) і перестає бути активним; нікуди не
    переходить — це робить `SessionService`. `signedOutUrl(accounts)` — єдине
    правило «є збережені акаунти — `/relogin`, нема — `/login`».
    `login(email, password, server?, replaceAccountId?)` входить на заданому
    сервері (за замовчуванням поточному); `adoptTokens` додає акаунт із пари
    токенів і робить його активним (його ж викликає сторінка `/join`).
    `forgetActive()` і `revoke(account)` — дві половини виходу: забути активний
    акаунт (віддає його запис із токенами) і відкликати його refresh-токен на
    сервері;
  - `authInterceptor` — додає `Authorization: Bearer <accessToken>` до
    запитів до `/api/...` (крім входу, виходу, оновлення токенів, статусу
    системи, умов до пароля, `GET /loginpageimages/random`, `POST /users`, запрошень —
    `GET /invitations/validate`, `POST /invitations/accept` — і нового пароля за посиланням,
    `POST /users/reset-password`); прострочений за
    `exp` токен оновлює до запиту, а на 401 оновлює токени й повторює запит
    один раз. Якщо оновити токени не вдалося — сесія акаунта завершується
    (`expireSession`), а сам запит не надсилається: той, хто його робив, отримує
    401 (чи «відповіді нема», якщо сервер мовчить). Запит іде з токеном акаунта,
    який був активним, коли запит створили;
  - `SessionService` — у фоні оновлює токени перед завершенням терміну
    access-токена (також коли вкладка знову стає видимою). Окремо оновлює
    токени **неактивних** акаунтів, у яких минула половина терміну
    refresh-токена: після завершення пошуку акаунта, при поверненні вкладки у
    фокус і раз на годину. Термін refresh-токена клієнт не знає (сервер його не
    віддає), тому припускає 7 днів, як у налаштуваннях API за замовчуванням.
    Відхилені токени позначають акаунт застарілим, мережева помилка нічого не
    змінює. Якщо токени зникли, а ми не на `/login` чи `/relogin`, переносить на
    `/relogin` (акаунти лишились, але активного нема) або на `/login` (під час
    пошуку акаунта ця перевірка мовчить);
  - `CurrentUserService` (`core/users`) — `GET /users/me`: підтверджує вхід і
    дає профіль для меню та форм, записує знімок профілю (разом із ролями
    користувача, `roles`), назву й посилання на логотип ГО в запис акаунта.
    Відповідь звіряється з контрактом: `id` (непорожній), пошта й імена мають бути
    рядками, інакше перевірка входу — `unavailable`; необовʼязкові поля не того
    типу відкидаються. Запит спільний лише для того самого акаунта; якщо, поки він
    ішов, активним став інший, результат — `unavailable` (не `unauthorized`: токени
    того акаунта тут ні до чого). 404 від API (тіло — ProblemDetails зі `status: 404`)
    означає, що користувача вже нема (акаунт видалили): сесія акаунта закінчується —
    він стає застарілим і неактивним, і `SessionService` веде на `/relogin`. 404 без
    такого тіла (проксі, інший сервіс за адресою) — `unavailable`.
    Разом з кожним таким запитом іде `GET /users/me/permissions`: права пишуться в запис акаунта
    (`permissions`) і доступні сигналом `permissions`; невдалий запит лишає
    попередній список. Сервер дає права за ролями з токена (claim `role_id`, читає
    `readJwtRoleIds`), а не за поточними, поки токен не оновлено. Тому, якщо ролі в профілі не
    збігаються з ролями токена (ролі змінив адміністратор), токени спершу оновлюються
    (`AuthService.refresh`), а права запитуються вже з новим. Сервер при цьому старий токен не
    відкликає (передано бекенду). `ensure()` не робить запиту, якщо профіль уже
    завантажено, а `reload()` перепитує його завжди (це викликає `authGuard`
    при зміні сторінки). Коли активним стає інший акаунт, профіль попереднього
    забувається, а новий завантажує той, хто зробив акаунт активним (пошук,
    перемикання чи страж сторінки після входу). Тимчасове перемикання активного
    акаунта (пошук, `activate`) профіль не скидає: `user` лишається профілем
    попереднього акаунта, а `profileLoaded` показує, чи профіль належить
    активному. Рейл, пункти меню й активна плитка слідують за акаунтом, який
    оновлюється лише після завершення перемикання. `permissionsSettled()`
    завершується, коли права з
    останнього запиту вже у знімку акаунта (на нього чекає
    `requireAnyPermission`). `applyLocal()` застосовує збережені зміни без
    запиту.
    Кожен із цих шляхів застосовує `preferredLanguage` профілю до мови
    інтерфейсу (див. «Локалізація»);
  - `UsersService` (`core/users`) — створення користувача, `GET /users`
    (сторінка колег разом із вимкненими, `ShowDeleted=true`, і з пошуком `SearchTerm`, якщо
    він є — від 3 до 100 символів, `SEARCH_MIN_LENGTH` і `SEARCH_MAX_LENGTH`: `id`, пошта,
    прізвище, імʼя й по батькові, `isActive`, а якщо сервер віддає — телефон, країна,
    екстрений контакт, займенники з категорією, аватар і ролі; `hasNextPage`),
    `GET /users/{id}` (`get`, профіль колеги),
    `POST /users/{id}/deactivate`, `POST /users/{id}/activate`, `DELETE /users/{id}`,
    `POST` і `DELETE` `/users/{id}/roles/{roleId}` (`assignRole`, `removeRole`),
    `POST /users/{id}/password-reset-token` (`createPasswordResetToken`, токен для посилання
    скидання пароля), `POST /users/reset-password` (`resetPassword`, новий пароль за токеном
    на сервері посилання, без авторизації),
    `GET /users/me/permissions`, `PUT /users/me` (оновлення профілю),
    `POST /users/me/avatar` (завантаження аватара) — обидва з необовʼязковим `userId`
    ідуть на `/users/{id}` і `/users/{id}/avatar` колеги — і
    `POST /users/me/password` (зміна пароля);
  - `NgoService` (`core/ngo`) — створення організації (лише назва),
    завантаження логотипа (`POST /api/v1/ngo/logo`, після нього
    організація читається заново), оновлення назви (`PUT /api/v1/ngo`; успіх
    оновлює назву в знімку акаунта, логотип лишається) і читання її
    назви та посилання на логотип (`fetch(server?)`);
  - `InvitationsService` (`core/invitations`) — `POST /api/v1/invitations`
    (`invite(email, roleIds)`: токен і `expiresAt`), `GET …/validate` (пошта
    запрошення) і `POST …/accept` (реєстрація колеги, віддає пару токенів); сервер
    для двох останніх задається явно;
  - `ProtectedImageService` (`core/http`) і директива `appProtectedSrc`
    (`shared/protected-src`): `GET` логотипа ГО й аватара вимагають токен, тож
    звичайний `<img src>` дав би 401. Зображення за `/api/` активного сервера
    (крім публічних `loginpageimages`) завантажується через `HttpClient`
    (токен додає інтерцептор) і кладеться в `src` як `blob:`; помилка
    завантаження викликає `error` елемента, тож працюють повернення до літер
    чи порожній блок. Використовується в аватарі (`app-avatar`), значку
    логотипа в меню акаунта та формі організації. Кеш у памʼяті належить
    сесії: при зміні активного акаунта (вихід, вхід, перемикання) він
    очищується, щоб закрите зображення одного користувача не потрапило до
    іншого без запиту до сервера. Кожне зображення, що показується, береться
    директивою в користування й віддається при зміні адреси чи знищенні
    елемента; кеш тримає не більше 30 повнорозмірних зображень, а при
    переповненні звільняє лише ті, що не використовуються, починаючи з
    найдавніше використаних, тож зображення на екрані не зникає;
  - `ThumbnailService` (`core/images`): стискає зображення до квадрата
    (аватар 96×96 з обрізанням по центру, логотип 64×64 цілком, прозорість
    зберігається) у `data:`-посилання WebP. Мініатюри лежать у записі акаунта
    (`avatarThumb`, `ngoLogoThumb`: адреса, з якої зроблено, і саме
    зображення). Їх робить `CurrentUserService` для активного акаунта при
    кожному оновленні профілю й організації, але лише коли змінилась адреса
    зображення (`?v=…`); мініатюри неактивних акаунтів у фоні не оновлюються.
    Плитки в меню акаунтів малюються з них без запитів, бо закрите
    зображення можна завантажити лише з токеном активного акаунта; мініатюра
    зі старої адреси не використовується, а видаляються мініатюри лише разом
    з акаунтом;
  - `LoginPageImagesService` (`core/login-page-images`) —
    `GET /api/v1/loginpageimages` (одна сторінка за запит, відносні
    посилання перераховуються від адреси сервера), `DELETE …/{id}` (`404`
    вважається видаленим), `POST` (`multipart/form-data`, поле `file`;
    `id` у відповіді не читається — галерея однаково перечитує список, тож і
    відповідь без нього — успіх) і `GET …/random` (випадкове зображення для сторінки входу,
    публічний запит; `random(server?)` питає й сервер, що ще не став поточним);
  - сервер і акаунт однієї дії запамʼятовуються на її початку: якщо, поки вона
    триває, активним став інший акаунт, решта запитів дії (права ролі, повторне
    читання організації) іде на той самий сервер, а результат пишеться в той самий
    акаунт. Таймаути запитів спільні — `core/http/timeouts.ts` (10 с на звичайний
    запит, 60 с на завантаження файлу).
- **«Вийти».** Видаляє лише активний акаунт (запис, індекс, вказівник активного;
  мова й інші акаунти лишаються) і відкликає його refresh-токен
  (`POST /api/v1/auth/logout`). Далі та сама перевірка, що й при вході на
  сторінку: знайшовся інший чинний акаунт — він стає активним і відкривається
  `REDIRECT_URL`; нема — `/relogin`, якщо акаунти ще є, інакше `/login`. Сценарій
  веде `AccountRestoreService.signOut`: пошук починається одразу після забування
  акаунта, не чекаючи відповіді сервера на відкликання. Акаунт зникає в усіх
  вкладках: та, де він теж був активним, переходить на `/relogin` чи `/login`, а
  вкладки з іншим активним акаунтом вихід не зачіпає. Повне очищення сховища
  (`localStorage` і `sessionStorage` вкладки) лишилось лише в «змінити адресу
  сервера» на `/login`.
- **Додавання акаунта.** Кнопка «+» в меню акаунта відкриває вікно «Додати акаунт»
  (`core/layout/add-account` на `shared/modal`): заголовок із хрестиком і спільна
  форма входу (`app-sign-in-form`, див. «Сторінка входу») з полем адреси сервера.
  Виклик `open(email?, accountId?, server?)`: `email` вписується в поле пошти,
  `server` — у поле адреси замість поточного, `accountId` — ключ збереженого
  акаунта. Якщо ключ є, заголовок вікна «Ввійти в акаунт» (а не «Додати акаунт»), а
  поруч із хрестиком стоїть смітник: він видаляє цей акаунт з памʼяті (запис,
  індекс, токени; решта памʼяті й інші акаунти лишаються) і закриває вікно.
  Форма малюється заново при кожному відкритті (нічого з минулого разу не
  лишається), а поки вікно закрите, її нема. Після входу вікно закривається,
  підключення перевіряється на сервері акаунта, відкривається `REDIRECT_URL` (зі
  стражами заново).
- **Меню акаунта.** Аватар у бічній панелі відкриває спливаюче вікно
  (`shared/popover`), а в ньому `core/layout/account-menu`: список акаунтів,
  кнопка додавання, «Налаштування профілю» й «Вийти». Колір аватара без
  зображення рахується з імені, прізвища й назви ГО (`shared/avatar`, алгоритм
  у `avatar-color.ts`, контраст ≥ 4.5:1 і з білим, і з чорним). Список
  акаунтів береться зі збережених у `localStorage` (знімок профілю й ГО в
  записі акаунта; аватар і значок логотипа малюються з мініатюр у записі, без
  запитів), у порядку додавання; активний має білу
  рамку; значок ліворуч унизу за прапорцями: `unavailable` — жовта
  `sync-circle`, `outdated` (з `unavailable` чи без) — червона `alert-circle`;
  аватар сірий лише в `outdated`: літери на сірому тлі, а зображення (якщо є) в
  градаціях сірого. При наведенні браузер показує
  підказку (`title`): у першому рядку «ПІБ — Назва ГО», у другому (якщо треба)
  «Відсутнє підключення до сервера» (`unavailable`, має перевагу) або «Сеанс
  закінчився» (`outdated`).
  Значок логотипа ГО праворуч унизу показується, коли в ГО є логотип (мініатюра
  в записі акаунта); без логотипа плитка лишається без значка. Нижче
  «Налаштування профілю» (веде на `/settings`, відкриває «Особисті дані») й
  «Вийти». Клацання по плитці закриває меню й:
  - активний акаунт — нічого більше;
  - чинний (`outdated: false`) — перемикання (`AccountRestoreService.activate`) і
    перехід на `REDIRECT_URL` (зі стражами заново);
  - застарілий (`outdated`, сервер відхилив токени; разом з `unavailable` чи без;
    правило `needsSignIn` з `account-login.ts`, те саме на `/relogin`) — вікно
    входу («Ввійти в акаунт») з його сервером, поштою й ключем (збіглася пошта — акаунт
    перезапишеться), без спроби підключитися;
  - лише недоступний (`unavailable`, не `outdated`) — повторна спроба
    (`activate`: сервер, оновлення токенів, профіль): вдалася — акаунт знову
    чинний і активний; ні — вікно входу;
  - чинний, який при перемиканні виявився недійсним, — теж вікно входу;
    активним лишається попередній.
- **Налаштування** (`/settings`). Друга бічна панель «Мої налаштування»
  (`core/layout/secondary-panel`) з пунктами-посиланнями; кожна вкладка має
  власну адресу: `/settings/personal-data` («Особисті дані», її відкриває й
  `/settings`), `/settings/password` («Зміна пароля»),
  `/settings/notifications` («Сповіщення»). Вкладки — окремі сторінки в
  `router-outlet` сторінки `settings`; спільні стилі форм —
  `settings/settings-section.scss` (однорядкові поля й вибори — 40px заввишки, як і решта
  однорядкових полів застосунку). Пункт «Сповіщення» приховано глобальним
  класом `.planned` (`src/global.scss`): елемент
  лишається в розмітці, але не показується, доки функція не готова.
  - **Дані профілю.** Поля, аватар і «Зберегти» — спільна форма профілю
    (`shared/profile-form`, та сама в «Редагувати» колеги). Власного запиту при
    відкритті вкладка не робить: поля
    беруться з профілю поточного користувача (`GET /api/v1/users/me`, який
    `authGuard` перепитує при кожній зміні сторінки й який оновлює знімок
    профілю в записі акаунта). Свіжий профіль заповнює поля, лише доки в них
    нічого не змінювали, і знову — після вдалого збереження: введене не
    стирається. Поля:
    прізвище, імʼя, по батькові, номер телефону, екстрений
    контакт, країна перебування, мова інтерфейсу, займенники, аватар (PNG,
    WebP, JPEG, JPG, GIF, BMP або SVG до 5 МБ; інший тип чи більший файл
    відхиляється помилкою під блоком аватара; пошти на сторінці нема: змінити її цим запитом
    API не дозволяє). Обовʼязкові (позначені `*`): прізвище, імʼя, займенники; решта
    необовʼязкові. Займенники — радіокнопки «Вона/її»,
    «Він/його», «Вони/їх» та «Інше» (з полем для свого варіанта); текст і
    категорія (`PronounCategory`: 1 — чоловічі, 2 — жіночі, 3 — нейтральні)
    передаються окремими полями. Номер телефону перевіряється на клієнті
    (`shared/phone`); порожній необовʼязковий рядок передається як `null`.
    «Зберегти» → `PUT /api/v1/users/me` (жодних прав не потрібно, лише
    авторизація); помилки полів показуються під ними, відповідь сервера —
    блоком зверху, після відповіді сторінка прокручується вгору. Поле «Мова
    інтерфейсу» будується зі списку мов (див. «Локалізація»). Якщо обрано файл
    аватара, після успішного `PUT` іде додатковий запит
    `POST /api/v1/users/me/avatar` (`multipart/form-data`, поле `file`; лише
    авторизація) із самим зображенням, а потім профіль перечитується
    (`GET /users/me`). Файл не обрано — цього запиту нема. Результат
    показується після обох запитів; невдача завантаження — червоний блок «Дані
    збережено, але аватар не змінено: …» (тексти в
    `settings.personal.result.avatar.*`), файл лишається обраним для повторної
    спроби. `PUT /users/me` аватара не містить і не змінює. Відповідність
    текстів займенників категоріям — припущення клієнта. При відкритті готовий
    варіант вибирається за категорією з профілю (`pronounCategory`), а не за
    текстом: текст збережено мовою, що була тоді; без категорії текст іде в «Інше».
  - **Зміна пароля.** Поле поточного пароля, новий пароль і повтор
    (`shared/password-fields`, умови сервера активного акаунта — див. «Умови до
    пароля»; відмічаються під час введення). `POST /api/v1/users/me/password`;
    пароль не логується. Повні
    правила перевіряє сервер (`400` показується як «Невдала спроба…»), клієнт
    лише дає швидкий відгук. Результат — блок: червоний для помилки, зелений
    для успіху.
- **Адмін** (`/admin-panel`). Сторінка з формою організації; весь вміст за
  правами користувача (права з `GET /users/me/permissions`, зі знімка акаунта;
  оновлюються при кожній зміні сторінки). Саму сторінку пускає
  `requireAnyPermission` (див. «Стражі сторінок»); блоки всередині (права
  наведено без префікса `Permissions.`):

  | Що на сторінці                   | Коли показується                                          |
  |----------------------------------|-----------------------------------------------------------|
  | Назва й логотип організації      | є `UpdateNgo`                                             |
  | Галерея зображень сторінки входу | є `CreateLoginPageImages` **або** `DeleteLoginPageImages` |
  | Кнопка видалення на зображенні   | є `DeleteLoginPageImages`                                 |
  | Плитка додавання в кінці галереї | є `CreateLoginPageImages`                                 |

  Заголовок «Адмін» і одна кнопка «Зберегти» (під галереєю, спільна на всю
  форму) показуються завжди; кнопка блокується на час запиту й має текст
  «Зберігаємо…». Частини форми незалежні, кожну веде своє право: назву й
  логотип — лише `UpdateNgo`, завантаження зображень — лише
  `CreateLoginPageImages`, видалення — лише `DeleteLoginPageImages`.
  - **Назва** — обовʼязкове поле до 200 символів; початкове значення —
    `ngoName` зі знімка акаунта, і воно підхоплює оновлення, поки назву не
    змінювали, і знову — після вдалого збереження.
  - **Логотип** — мініатюра 120×120 з вибором файлу (PNG, WebP, JPEG, JPG,
    GIF, BMP або SVG до 5 МБ; ті самі правила, що в логотипа на сторінці входу;
    формати й розмір задано в `core/images/image-types.ts`, довжину назви — у
    `core/ngo/logo-rules.ts`). Формати й найбільший розмір однакові для всіх
    зображень (аватар, логотип, зображення сторінки входу), як на сервері: 5 МБ
    на весь запит, тож сам файл перевіряється з невеликим запасом
    (`IMAGE_MAX_BYTES`), а в текстах розмір стоїть на місці `{{size}}`
    (`IMAGE_MAX_MEGABYTES`). Відповідь `413` при завантаженні — на сервері скінчилося
    місце для файлів (`UploadFailure` `quotaExceeded`, `toUploadFailure`): кожне
    завантаження каже про це окремим текстом (`…quotaExceeded`), бо повтор не допоможе.
    Назви форматів у текстах сторінок теж беруться з цього файлу (`IMAGE_TYPE_NAMES`,
    масив): у мовному файлі на місці переліку стоїть `{{types}}`, а канал `listText`
    (`shared/list-text`) зʼєднує масив роздільником і сполучником мови
    (`common.list.*`). Обране зображення одразу показується в превʼю. Поки
    логотипа нема (або він не завантажився), показується порожній блок із
    пунктирною рамкою без літер і без заокруглення кутів.
  - **Збереження.** Кнопка одна, але запити частин незалежні (адреси
    відносно `/api/v1`, права без префікса `Permissions.`):

    | Запит                          | Право                   | Коли надсилається            |
    |--------------------------------|-------------------------|------------------------------|
    | `PUT /ngo` (назва)             | `UpdateNgo`             | назва не порожня й змінилася |
    | `POST /ngo/logo` (логотип)     | `UpdateNgo`             | обрано файл                  |
    | `DELETE /loginpageimages/{id}` | `DeleteLoginPageImages` | є видалені зображення        |
    | `POST /loginpageimages`        | `CreateLoginPageImages` | є додані файли               |

    Порядок: спершу назва (`PUT /api/v1/ngo` з `{ name }`, логотип не змінює;
    лише якщо назва змінилася; назва без пробілів по краях), потім логотип
    (`POST /api/v1/ngo/logo` із самим зображенням, лише якщо обрано файл і
    `PUT`, якщо він був, вдався), потім видалення, потім завантаження
    галереї. Після успішного завантаження логотипа організація читається
    заново (`GET /api/v1/ngo`), нове посилання потрапляє в знімок акаунта, а
    обраний файл і превʼю забуваються. Порожня назва блокує `PUT` і логотип
    (помилка під полем), галерея зберігається все одно. Невдача однієї групи
    не зупиняє іншу; в межах групи запити йдуть по одному й зупиняються на
    першій невдачі.

    Результат — блок над формою з кількома рядками: форма може бути
    збережена не повністю, тож перелічується, що саме змінилося й що не
    вдалося.

    | Рядок                                              | Коли зʼявляється                        |
    |----------------------------------------------------|-----------------------------------------|
    | «Назву організації змінено.»                       | назва змінилась, `PUT` вдався           |
    | «Логотип організації змінено.»                     | файл обрано, `POST /ngo/logo` вдався    |
    | «Зображення сторінки входу змінено.»               | у галереї щось збережено                |
    | «Назву й логотип організації не змінено: …»        | `PUT` не вдався; логотип не надіслано   |
    | «Логотип організації не змінено: …»                | `POST /ngo/logo` не вдався; файл лишено |
    | «Зображення сторінки входу змінено не повністю: …» | запит галереї не вдався                 |

    Причини: `400` — сервер не прийняв дані, `401` — сесію завершено, `403` —
    недостатньо прав, відсутність відповіді — сервер не відповідає, інше —
    «спробуйте ще раз». Блок зелений, коли всі рядки успішні, і **червоний,
    якщо є хоч одна невдача** (успішні рядки в ньому теж видно). Нічого не
    змінювалось — блоку нема (і `PUT` не йде); блок зникає, щойно змінюють
    назву чи обирають файл. Тексти — у `admin.result.*` мовного файлу.

    Після успіху `PUT` назва записується в знімок акаунта в `localStorage` (у
    той акаунт, від імені якого йшов запит; логотип у знімку не змінюється), а
    після `POST /ngo/logo`
    знімок отримує нове посилання на логотип; при помилці сховище не
    змінюється. Поки галерея зберігається, замість її рядка крутиться прелоадер,
    а після відповіді — хоч би якою вона була — галерея скидається повністю (усі
    три списки, зокрема те, що зберегти не вдалося, і запит сторінки, що ще йде) й
    отримує список заново з першої сторінки.
  - **Галерея** (`admin-panel/images-gallery`) — зображення 8:10 заввишки
    200px в один рядок із прокруткою по X; на краю, за яким ще є зображення,
    градієнт у колір тла. Кнопка видалення зʼявляється при наведенні (на
    пристроях без наведення завжди видна), плитка додавання стоїть останньою.
    Коли її не видно, на правому краї рядка зʼявляється маленька кнопка «+»
    (як «Розгорнути» бічного меню, віддзеркалена). Додавання відкриває вибір
    файлу (ті самі формати й той самий найбільший розмір, 5 МБ, що для аватара й
    логотипа, як на сервері; інший файл відхиляється помилкою під рядком).
    - **Отримання списку.** При відкритті
      `GET /api/v1/loginpageimages?PageNumber=1&PageSize=20` (потрібне право
      `ViewLoginPageImages`; без нього запиту нема). Зображень може бути
      тисячі, тому далі підвантажується по одній сторінці, коли прокрутка
      наближається до кінця рядка (менше ~400px), а в кінці крутиться
      прелоадер; якщо рядок не заповнює вікно, сторінки добираються самі.
      Після помилки сторінки автоматично не повторюємо, а повторюємо, коли
      користувач знову докрутить до кінця. Немає зображень і немає права
      додавати — замість плитки блок «Наразі відсутні зображення для
      сторінки входу»; з правом додавати лишається плитка з плюсом.
    - **Три списки.** Зміни користувача лежать у трьох списках і на сервер
      йдуть лише за «Зберегти»: (1) зображення з системи; (2) зображення з
      системи, видалені користувачем (переносяться сюди з першого);
      (3) файли, додані користувачем. Видалення доданого файлу просто
      прибирає його з третього списку. Видалені не зʼявляються повторно,
      навіть якщо сервер віддасть їх на наступній сторінці. На час
      збереження додавання й видалення в галереї не приймаються, а після нього
      галерея скидається (див. «Збереження» вище).
  - **Обмеження:** скасувати
    видалення до збереження не можна (лише перезавантажити сторінку, що
    скидає всі незбережені зміни); підтвердження перед видаленням нема;
    запитів багато — по одному на кожне видалення й завантаження.

  **Меню дій і права.** Три крапки в кінці рядка відкривають спливаюче меню дій
  (`app-popover` зі спільним `app-action-list`). Кнопки «Ролі» й «Додати» та
  пункт «Редагувати» відкривають бічне вікно
  (`app-side-panel`); зміст у ньому поки є в «Ролей», «Додати» й «Редагувати». «Вимкнути
  акаунт», «Ввімкнути акаунт», «Видалити» й «Скинути пароль» працюють (див. нижче); **для
  решти дій меню й «+» нічого не зроблено.** Що показується, залежить від прав (зі
  префікса `Permissions.`):

  | Що на сторінці                         | Коли показується                         |
  |----------------------------------------|------------------------------------------|
  | Вкладка в бічному меню й сама сторінка | є `ViewUser`                             |
  | Кнопка «Додати»                        | є `CreateUser`                           |
  | Три крапки в кінці рядків              | є хоча б один пункт меню дій             |
  | Кнопка «+» у заголовках таблиці        | є `ViewCustomFields` (поки `planned`)    |

  Меню біля трьох крапок складається з пунктів, кожен із яких
  показується за своїм правом (права без префікса `Permissions.`); три крапки
  є, коли доступний хоча б один пункт, інакше комірка в кінці рядка лишається
  порожньою, щоб таблиця не зсувалась. Поки меню відкрите, рядок лишається
  виділеним. Для рядка самого користувача (`id` рядка збігається з `id`
  профілю, а поки його нема, зі `userId` знімка акаунта) меню має єдиний пункт
  «Налаштування профілю» (як у меню акаунтів, без прав, веде на `/settings`),
  решта пунктів не показується.

  | Пункт меню                | Коли показується                                  |
  |---------------------------|---------------------------------------------------|
  | Редагувати                | є `UpdateUser` **і** `ViewUser`                   |
  | Ролі у формі «Редагувати» | є `AssignRoleToUser` (і права «Редагувати»)       |
  | Скинути пароль            | є `CanResetPassword`                              |
  | Вимкнути акаунт           | є `DisableUser`                                   |
  | Ввімкнути акаунт          | є `UpdateUser`                                    |
  | Видалити                  | є `DeleteUser`                                    |

  Окремого пункту «Змінити ролі» нема: ролі колеги змінюються у формі «Редагувати»
  (`AssignRoleToUser`), а самі ролі — у вікні «Ролі» (`ManageRole`). У формі ролі обидва
  права вмикаються разом, групою «Керування ролями».

  Можливо, згодом це доведеться виправити: «Редагувати» вимагає `UpdateUser`, а запити ролей
  колеги (`POST`/`DELETE /api/v1/users/{id}/roles/{roleId}`) — лише `AssignRoleToUser`. Тож той, у
  кого є `AssignRoleToUser` без `UpdateUser`, ролей колеги змінити не може, хоча сервер дозволив би
  (тоді потрібен окремий пункт для ролей).

  Із пунктів «Вимкнути акаунт» і «Ввімкнути акаунт» видно лише той, що підходить
  стану колеги (`isActive` з `GET /users`): «Вимкнути» — для ввімкненого,
  «Ввімкнути» — для вимкненого; порожнє меню (наприклад, є лише `DisableUser`, а
  акаунт уже вимкнено) не відкривається. Вимкнений колега в таблиці — із сірим
  аватаром, приглушеним імʼям та іконкою `person-remove` перед ним.

  **Редагування колеги.** «Редагувати» (`UpdateUser` разом із `ViewUser`: форма спершу читає профіль
  колеги) відкриває бічне вікно із заголовком «Дані колеги» в шапці (на одній висоті з хрестиком) й
  питає профіль колеги `GET /api/v1/users/{id}` (`UsersService.get`; ті самі поля, що й

  (`colleagues.profileForm.loadError.*`); відповідь для колеги, для якого вікно вже не відкрите,
  ігнорується. Форма — спільна `app-profile-form` з «Даних профілю», заповнена з відповіді
  (займенники — за категорією, поле свого варіанта — «Займенники колеги»). Поле екстреного контакту
  — лише з правом `ViewEmergencyContact` (без нього сервер віддає `null`). З правом
  `AssignRoleToUser` перед «Зберегти» ще й «Ролі» плашками (`colleagues/role-choices`, як у формі
  нового колеги; список — `GET /api/v1/roles`, спершу вибрані ролі колеги з профілю; без права ролі
  не запитуються); хоча б одна роль обовʼязкова, як у формі нового колеги (зірочка біля «Ролі»; без
  ролі «Зберегти» нічого не надсилає й показує «Оберіть хоча б одну роль.», вибір ролі ховає
  помилку). «Зберегти» (`saveColleague`): `PUT /api/v1/users/{id}` з полями форми (без поля
  екстреного контакту — `emergencyContact: null`; сервер тоді лишає наявний: без
  `ViewEmergencyContact` чужого контакту не змінити); якщо обрано файл — `POST
  /api/v1/users/{id}/avatar`; з `AssignRoleToUser` —
  ролі за різницею вибраних із тими, що колега має: нові — `POST /api/v1/users/{id}/roles/{roleId}`,
  зняті — `DELETE` (по одному запиту, спершу нові, тоді зняті: сервер не приймає одночасних змін
  ролей одного користувача, 400 «Optimistic concurrency failure»; без змін — без запитів). Невдалий
  `PUT` зупиняє збереження («Не вдалося зберегти дані колеги: …»,
  `colleagues.profileForm.saveError.*`). Невдача аватара чи ролі не зупиняє решту: вікно лишається
  відкритим з помилкою за кожну частину (`avatarError.*`, `rolesError.*` — «Дані збережено, але …»)
  над «Зберегти», а повторне збереження робить лише те, що лишилося (вдалі зміни ролей
  запамʼятовуються). Усе вдалося — вікно закривається; після будь-якої вдалої зміни список колег
  запитується заново. Зміна поля чи ролі ховає помилки.

  Чекає на зміну API: займенники у спільній формі обовʼязкові, а в запрошених колег їх нема
  (запрошення займенників не питає). Щоб змінити такому колезі роль, доводиться вигадувати йому
  займенники. Потрібно, щоб сервер приймав профіль без займенників (чи щоб ролі змінювалися без
  збереження профілю); до того клієнт лишається як є.

  «Редагувати» викликає `editColleague` (див. вище) з
  колегою з рядка (`id` та імʼя з запиту, `{id, name}`; `name` — `null`, якщо
  імені нема) і відкриває бічне вікно; стан вікна (`panel`: що відкрито,
  `userId` й `userName` колеги) скидається при закритті. «Вимкнути акаунт» і
  «Видалити» показують підтвердження у вікні по центру екрана (як видалення ролі):
  «{ПІБ} втратить доступ до платформи. Ви зможете знову ввімкнути акаунт у разі
  потреби.» чи «{ПІБ} втратить доступ до платформи. Дані колеги буде повністю
  втрачено.» (колегу без імені названо поштою), і на «Так» шлють
  `POST /users/{id}/deactivate` чи `DELETE /users/{id}`. «Скинути пароль» питає так само:
  «{ПІБ} зможе задати новий пароль за посиланням, яким ви поділитеся. Поточний пароль
  діятиме, доки його не змінять. Створити посилання?», і на «Так» шле
  `POST /users/{id}/password-reset-token` (`UsersService.createPasswordResetToken`; сервер
  лише створює токен, старий пароль діє, доки колега не задасть новий). Успіх закриває
  питання й відкриває те саме вікно, що й «Запрошення створено», з `kind="passwordReset"`:
  «Посилання для скидання пароля створено», посилання `…/reset-password#token=…` за тим самим
  правилом хоста, пошта колеги й «Дійсне до» (тексти — `colleagues.passwordReset.*`, кнопки й
  статуси спільні з `colleagues.invitation.*`); невдача лишає питання з причиною
  (`colleagues.actionError.resetPassword.*`). Список колег після цього не оновлюється.
  Посилання відкриває сторінку `/reset-password` (див. «Сторінка нового пароля»).
  «Ввімкнути акаунт» одразу
  шле `POST /users/{id}/activate`. Успіх одразу змінює рядок (видалений зникає) і
  запитує список з першої сторінки заново з тим самим сортуванням. Невдача лишає
  вікно з причиною (400 — останній адміністратор чи власний акаунт), а для
  ввімкнення — повідомлення внизу екрана. Вмикання акаунта вимагає
  `UpdateUser`, а не `DisableUser`, бо так працює `POST /users/{id}/activate`
  на сервері. Право `ViewEmergencyContact` показує колонку «Екстрений контакт».
  Вкладку без `ViewUser` не пускає страж маршруту (див. «Стражі сторінок»).

  **Вікно «Ролі».** Кнопка «Ролі» в шапці відкриває бічне вікно на списку: при
  **кожному** відкритті йде `GET /api/v1/roles` (`RolesService`, `core/roles`:
  сторінки по 100, поки сервер каже `hasNextPage`; збій будь-якої сторінки це
  збій усього запиту, щоб неповний список не видавався за повний, і так само
  помилка, якщо сервер каже «є ще» й після 50 сторінок (запобіжник); для читання
  потрібна лише авторизація, тож список бачать усі, хто бачить вкладку). Поки
  йде оновлення, лишається попередній список, а запит, що ще триває, не
  дублюється. Ролі показані тегами (`app-role-pill`, колір за назвою), є стани
  «Завантажуємо ролі…», «Ролей ще нема.» і помилка за причиною
  (`colleagues.rolesPanel.*`).

  Керування ролями вимагає `ManageRole`; без нього вікно має лише заголовок,
  хрестик і список. З правом: зверху зліва, на одній висоті з хрестиком,
  кнопка «Додати роль» (слот `sidePanelHeader` вікна), а по правому краю
  кожного рядка кнопки «Редагувати» (олівець) і «Видалити» (смітник).
  «Видалити» питає підтвердження у вікні по центру екрана (`shared/confirm-dialog`
  у `app-modal`, як вікно входу в акаунт): «{роль} буде видалено.»,
  «Так» (червона) і «Скасувати». «Так» — `DELETE /api/v1/roles/{id}`
  (`RolesService.delete`); поки йде запит, кнопка вимкнена. Успіх закриває вікно,
  прибирає роль зі списку й оновлює його з сервера; невдача лишає вікно з причиною
  (`colleagues.rolesPanel.deleteError.*`; 400 — роль має хтось із колег або це
  системна роль адміністратора). «Додати роль» замінює
  список формою «Нова роль» (`app-role-form`), а кнопка в шапці стає «Назад»
  (список лишається без нового запиту): поля «Назва» (обовʼязкове),
  «Фемінітив» і «Множина» (до 256 символів, як на сервері) та кнопка
  «Додати», яка перевіряє назву й віддає дані (разом із правами вибраних
  груп) у `createRole(role)`. Над кнопкою стоять тумблери прав за таблицею
  «Назви прав» (спочатку всі вимкнені). Надати можна лише права, які є в
  самого користувача (з його профілю): тумблер групи доступний, коли є **всі**
  її права (для обʼєднаних груп перевірка за AND, `canGrantGroup`), інакше він
  вимкнений, рядок приглушений, а підказка пояснює причину. Підпункти
  (`parent` у `PERMISSION_GROUPS`): у «Перегляду колег» — перегляд екстрених
  контактів і додаткових полів, створення й редагування, скидання паролів, вимкнення
  й видалення, керування ролями; у «Перегляду таблиць» — керування таблицями.
  Підпункти стоять під своїм пунктом одним блоком (без ліній між ними), перед назвою —
  лінії дерева (CSS): у середніх вертикаль іде далі, в останнього закінчується
  заокругленим кутом. Поки пункт вимкнений, підпункти вимкнені й
  приглушені (підказка `permissionNeedsParent`), а вимкнення пункту вимикає й
  підпункти. Без пункту права підпунктів у роль не йдуть (`claimsOfGroups`): роль,
  що має їх без свого пункту, показано з вимкненими підпунктами, і збереження їх
  прибирає. «Додати» відправляє роль (`RolesService.create`): `POST /api/v1/roles` з назвами
  (порожні — `null`; у відповідь сервер віддає `{ id }`, хоч контракт описує голий
  рядок — беремо обидва, відповідь без `id` — помилка), а далі для кожного права окремий
  `POST /api/v1/roles/{id}/claims/{право}` по черзі (так сервер задає права;
  невдача одного не зупиняє решту): права вибраних груп і право без
  налаштування `ViewTableTemplate` (додається до кожної ролі в будь-якому
  випадку; `CreateNgo` лише в першого користувача, його не додаємо; права
  `ViewNgo` сервер більше не має: організацію бачить кожен, хто ввійшов).
  Поки йде відправка, кнопка вимкнена; успіх повертає до оновленого списку (якщо
  не всі права додалися, над списком попередження
  `colleagues.rolesPanel.noticePartial`), невдача створення лишає форму з
  помилкою за причиною (`colleagues.roleForm.saveError.*`). «Редагувати» питає
  роль у сервера (`GET /api/v1/roles/{id}`, `RolesService.get`, відповідь має ще
  й `claims`) і замість списку показує ту саму форму, заповнену назвами ролі:
  заголовок «Редагування ролі», кнопка «Зберегти» відправляє зміни
  (`RolesService.update`): `PUT /api/v1/roles/{id}` з
  `{newName, feminitiveName, pluralName}` (порожні необовʼязкові — `null`), а
  далі по черзі окремими запитами `POST` (додати) і `DELETE` (прибрати) на
  `/api/v1/roles/{id}/claims/{право}` за різницею з початковими `claims` ролі
  (`diffClaims`). Зачіпаються лише групи, які користувач може надати (є всі
  права групи, AND): увімкнена додає права, яких у ролі нема, вимкнена прибирає
  свої права (так виправляється й часткова група); недоступні групи й права поза
  групами (зокрема `ViewNgo` у ролях, створених до його видалення на сервері) не
  чіпаються; право без налаштування `ViewTableTemplate` додається, якщо його
  нема. Невдача окремого права не зупиняє решту. Поки йде відправка, кнопка
  вимкнена; успіх повертає до оновленого списку (якщо якусь зміну прав не
  вдалося застосувати, над списком попередження
  `colleagues.rolesPanel.noticePartialUpdate`), невдача збереження назв лишає
  форму з помилкою (`colleagues.roleForm.updateError.*`), права не чіпаються.
  Тумблери прав заповнюються з `claims` ролі: група ввімкнена, коли в ролі є всі
  її права; часткова (є лише частина прав) лишається вимкненою й позначається
  іконкою `alert-circle-outline` із підказкою при наведенні чи фокусі: проблема
  з роллю, яку виправить оновлення ролі (`colleagues.roleForm.partialTitle`,
  `partialNote`). Доступність така сама, як у формі нової ролі (за правами
  користувача, AND), але заблокована група показує стан ролі, і змінити його не
  можна. Поки йде запит, на місці форми «Завантажуємо роль…», при помилці її
  причина (`colleagues.roleForm.loadError.*`); «Назад» повертає до списку, а
  відповідь, що прийшла після нього чи для іншої ролі, ігнорується. «Ролі»
  завжди відкривають вікно на списку; якщо право зникло при відкритій формі,
  показується список.

  **Вікно «Додати колегу».** Кнопка «Додати» (з `CreateUser`) відкриває бічне
  вікно із заголовком «Додати колегу» в шапці (на одній висоті з хрестиком) і формою
  `app-colleague-form`. Ролі для неї запитуються так само, як
  для вікна «Ролі» (`GET /api/v1/roles` при кожному відкритті, спільний стан
  `rolesView`, ті самі повідомлення про завантаження, порожній список і
  помилку). Поля: «Пошта» (обовʼязкове, `type=email`; після першої спроби
  відправки показується «Введіть пошту.» або «Введіть коректну пошту.»,
  перевірка та сама, що на сервері (`shared/email`)) і
  «Ролі»: вибір плашками (`colleagues/role-choices` на `app-role-pill`, можна вибрати
  кілька, кнопка-прапорець `role="checkbox"` з `aria-checked`; потрібна хоча б одна, на
  підписі стоїть позначка обовʼязковості, а після першої спроби без вибору — «Оберіть хоча б одну
  роль.»): вибрана роль залита кольором і має іконку `checkmark-circle`, невибрана
  має рамку й іконку `ellipse-outline`. Кнопка «Додати» перевіряє пошту й ролі й
  відправляє запрошення (`InvitationsService.invite`): `POST /api/v1/invitations` з
  `{email, roleIds}`. Колегу це ще не створює: сервер віддає токен, за яким він
  завершує реєстрацію на `/join`. Поки йде запит, кнопка вимкнена; помилка
  (`colleagues.colleagueForm.saveError.*`; `409` — колега з такою поштою вже має
  акаунт) лишає форму з повідомленням. Успіх: форма
  скидається, бічне вікно закривається, відкривається діалог запрошення
  (`app-invitation-dialog` у `app-modal`): «Запрошення створено» з хрестиком,
  посилання `…/join?token=…` на хост сервера, де створено запрошення (той самий хост,
  що в сторінки, — адреса сторінки; інший — його домен зі стандартним портом; один
  рядок з прокруткою), кнопка копіювання
  (Clipboard API) і, якщо браузер підтримує, «Поділитися» (Web Share API: заголовок,
  текст із назвою ГО й датою дії та посилання; скасування вибору — не помилка),
  пошта й «Дійсне до». Тексти — `colleagues.invitation.*`. Токен видно лише тут:
  списку запрошень API не віддає. Те саме вікно показує й посилання для скидання пароля (див.
  «Меню дій і права»).
- **База знань** (`/knowledge-base`). Друга панель — дерево розділу, основний блок — вид за
  адресою (`knowledge-base.routes.ts`, у `router-outlet` сторінки):
  - «Посібник» — `/knowledge-base`;
  - таблиця — `/knowledge-base/tables/:id` (вхід `id`; див. «Вид таблиці» нижче);
  - сторінка — `/knowledge-base/pages/:id` (запланована: назва зі змісту й заглушка
    `knowledgeBase.page.planned`);
  - менеджер шаблонів — `/knowledge-base/templates` (див. нижче).

  Сторінка `KnowledgeBasePage` лише завантажує зміст і дає відступи; таблиця чи сторінка, якої нема
  в змісті (видалили чи стара адреса), веде на «Посібник» (`injectKnowledgeBaseEntry`). І дерево,
  і «Посібник» будуються з одного змісту, який підвантажує `KnowledgeBaseService`
  (`core/knowledge-base`; один запит на обох, далі спільний): масив, де кожен елемент — матеріал
  (`id`, тип і назва: `customtable` — таблиця, `page` — сторінка) чи папка (`type: "folder"`, `id`,
  `title` і матеріали в ній, `items`: лише таблиці й сторінки); без `id` чи назви елемент
  відкидається, невідомі типи пропускаються. Головної сервер не віддає: клієнт додає її на початок
  (`withHomePage`), а «Головна» — з мовного файлу (`common.home`). Відповідь не за цією формою
  відкидається поелементно (`toKnowledgeBaseEntries`). Звідки зміст — токен
  `KNOWLEDGE_BASE_SOURCE`: `customtables` (зараз) — список таблиць організації `GET <сервер
  активного акаунта>/api/v1/customtables` (усі сторінки по 100, за назвою; у змісті лише таблиці в
  корені, без папок і сторінок); `tree` — загальний запит `…/api/v1/knowledge-base/tree`, коли
  бекенд його зробить (шлях умовний); `sample` — файл `src/assets/knowledge-base/sample.json` у
  тому самому форматі (для перевірки вигляду папок і сторінок). Завантаження змісту — задача
  `PendingTasks` (його дочікується `whenStable`). Поки йде запит —
  «Завантажуємо зміст…», невдача — повідомлення (на сторінці з «Спробувати ще раз»). Дерево: головна
  — посилання на `/knowledge-base`, групи — папка (`folder-outline`) з назвою розділу й сторінки;
  назва групи — кнопка згортання (`aria-expanded`): клік згортає групу, повторний — розгортає (стан
  за `id` папки запамʼятовується в `localStorage`, `yavir.knowledgeBase.collapsedFolders`), а при
  наведенні папка змінюється на стрілку (розгорнута — `chevron-down-outline`, згорнута —
  `chevron-forward-outline`); перший пункт («Головна») має відступ 6px згори — на одній висоті з
  вітальним блоком «Посібника»; групи відступають від сусідів більше (по 8px згори й знизу); у
  плашці папки при наведенні перед трьома крапками — «+» (додати в папку), окремі сторінки —
  пункти з іконкою за типом (сторінка — `document-outline`, таблиця (`customtable`) —
  `grid-outline`) — посилання на свій вид (`knowledgeBaseLink`), відкритий рядок виділений
  (`routerLinkActive` на рядку); на телефоні вибір пункту закриває бокове меню. «Посібник»
  (`knowledge-base/kb-contents`; назва матеріалу в ньому — теж посилання на вид):
  заголовок `knowledgeBase.guide` (24px), рамка з 👋 і вітальним текстом (`knowledgeBase.intro`),
  сітка блоків (колонки щонайменше 280px, скільки вміщується; блоки йдуть рядками): група — назва з
  лінією під нею (плашка завжди як наведена: підложка, обрис згори й з боків, видимі «+» і три
  крапки) і список сторінок; усі матеріали без папки — один блок-стовпчик (на місці першого з
  них), а не окремий блок кожен; головної в сітці нема (це сам «Посібник»). Ні таблиць, ні
  сторінок, ні папок — замість сітки порожній стан (`app-empty-state`). Відступи основного
  блоку — як у «Адмін», лише зверху 17px, щоб «Посібник» стояв на
  рівні з заголовком другої панелі. Шапка з кнопкою меню й «База знань» — лише до 992px, де дерева
  не видно. Розміри шрифтів «Посібника» — як на сторінці «Адмін»: заголовок 24px, назви груп (жирні,
  шрифт заголовків), сторінки й вітальний текст — 15px. У дереві й у «Посібнику» при наведенні (чи
  фокусі з клавіатури, `:focus-visible` — після кліку мишею підсвітка не лишається) сторінка чи
  назва групи виділяється підложкою, а біля назви зʼявляються три крапки
  (`knowledgeBase.pageActions` / `groupActions`) — меню дій (`app-kb-item-menu`: та сама плашка, що
  в колег): для папки «Редагувати», «Видалити», на телефоні ще «Додати в папку» першим; для таблиці
  й сторінки «Редагувати», «Перемістити», «Видалити». У меню лише дії, на які є права
  (`KnowledgeBaseService.can`, права для кожного типу — `KNOWLEDGE_BASE_RIGHTS`); нема жодної —
  нема й трьох крапок. «Перемістити» заплановане (`planned`: сервер ще не вміє). «Додати в папку»
  — `requestInsert` з папкою; решта відкриває вікно по центру екрана (`app-modal`, шапка
  `app-dialog-header` з назвою дії й хрестиком; форма — `kb-item-form`):
  - «Редагувати» (`UpdateCustomTable`) — читає таблицю (`GET /api/v1/customtables/{id}`) і
    запамʼятовує структуру; форма з назвою (обовʼязкова) й описом; «Зберегти» — `PUT
    /api/v1/customtables/{id}` з новими назвою й описом і тими самими полями (сервер приймає
    назву й опис лише разом зі структурою); нічого не змінилося — вікно просто закривається;
  - «Видалити» (`DeleteCustomTable`) — «„{{title}}“ буде видалено.» (для папки ще «Весь зміст
    папки буде втрачено.»), «Так» — `DELETE /api/v1/customtables/{id}`;
  - «Перемістити» — «З папки» (де матеріал зараз, лише показує) і «До папки» (усі папки й «Без
    папки»), поки лише в памʼяті.

  Невдача запиту лишає вікно відкритим з причиною (`knowledgeBase.failure.*`). Після успіху дерево
  й «Посібник» оновлюються одразу. Дії обирають запит за типом матеріалу (`switch`): зараз лише
  таблиці; для сторінок і папок — TODO (`unsupported`). «Головна» трьох крапок не має, на
  телефоні й планшеті (до 992px) у рядках лише три крапки — завжди видимі й більші
  (32px), «+» папки там нема. Ширина від цього не росте: у дереві назва й так в один рядок і
  обрізається трикрапкою, а в «Посібнику» місце під три крапки є завжди, тож назва в кілька рядків
  переноситься однаково з наведенням і без. Шапка бокового меню: «+», кнопка менеджера шаблонів
  (`layers-outline`, лише з `ViewTableTemplate`) і згортання — квадрати 36px (щоб «База знань»
  стояла в один рядок), при наведенні підложка `--nav-active-bg`, підказка — `title`. На
  телефоні (до 992px) шапки нема: у правому нижньому куті екрана над затемненням, поки меню
  відкрите, — синя кнопка менеджера шаблонів (закриває меню й відкриває менеджер) над зеленою «+».
  Додавання: «+» у плашці папки (дерево й «Посібник»), у шапці бокового меню і плаваюча «+» на
  телефоні — лише з `CreateCustomTable` (інакше кнопок нема). Вони передають місце в
  `KnowledgeBaseService.requestInsert`: папку (`id` і назва)
  чи корінь змісту (`folder: null`). Запит відкриває одне на весь застосунок вікно «Додати»
  (`kb-add-dialog` в `app.component`; у папці — «Додати в „{{title}}“»):
  - «Тип» — видимий, але вимкнений (вибрана «Таблиця»; сторінок і папок сервер ще не вміє);
  - «Шаблон» — «Без шаблону» й шаблони з `GET /api/v1/tabletemplates` (з правом
    `ViewTableTemplate`, інакше лише «Без шаблону»);
  - «Назва» (обовʼязкова, до 255 символів) і «Опис» (до 1000).

  «Створити»: із шаблоном — `POST /api/v1/customtables/from-template` (порожній опис сервер бере з
  шаблону), без шаблону — `POST /api/v1/customtables` з одним текстовим стовпчиком «Назва»
  (`name`; сервер вимагає хоча б одне поле); після успіху зміст завантажується заново.

  **Вид таблиці** (`knowledge-base/kb-table`). Шапка — як у «Колегах» (`app-search-header` на тлі
  шапки сторінки, на всю ширину основного блоку, 65px — на рівні з шапкою бокового меню):
  - назва зі змісту (після «Редагувати» оновлюється одразу) — до двох рядків (`titleLines`), далі
    трикрапка, повна — у підказці;
  - праворуч контурний зелений тег «Зміни збережено» (`cloud-done-outline`, розміром як плашки
    ролей, по центру висоти кнопок; до 600px — лише іконка, текст — для екранних читачів і в
    підказці; поки відкрито пошук — схований; стани — див. «Редагування»);
  - кнопки лише іконками з підказкою (`iconOnly`): «Створити шаблон» (`layers-outline`, синя, з
    `CreateTableTemplate`; див. нижче) і «Експортувати» (`share-outline`, з `ViewCustomRecord`;
    див. нижче);
  - лупа — пошук у записах (`SearchTerm` у запиті записів, як у «Колегах»).

  Під шапкою — опис приглушеним рядком і таблиця як список колег (`app-data-table`): на всю ширину
  основного блоку (виходить за його бічні відступи), масивний рядок заголовків, лінії між
  стовпчиками (`columnLines`), стовпчики по 220px (більше, ніж уміщується, — прокрутка вбік).
  Висота таблиці — щонайбільше до низу екрана (чи до смуги дій): вид — колонка на всю висоту
  змісту, записи прокручуються всередині таблиці, рядок заголовків лишається вгорі; на низькому
  екрані таблиця не менша за 200px, тоді прокручується сторінка.
  Стовпчики — поля таблиці в їхньому порядку (`GET /api/v1/customtables/{id}`), рядки — записи (`GET
  /api/v1/customrecords?CustomTableId=…`, усі сторінки по 100; право `ViewCustomRecord`, без нього
  записи не запитуються); значення — за `id` поля, усі — рядки (обовʼязковість `isRequired`
  не враховуємо — на сервері її приберуть; старе логічне значення — прапорцем `☑` / `☐`). Записів
  нема — під заголовками один порожній рядок. Сортування — кнопка-іконка в заголовку
  (`headerTemplate` в `app-data-table`):
  записи заново, відсортовані сервером за значенням поля (`OrderBy` — `id` поля; без сортування —
  порядок рядків, збережений сервером). «+» колонки й трьох крапок рядків нема, тож нема й їхньої
  колонки.

  **Редагування** (з `UpdateCustomTable`):
  - опис — по кліку (поле на місці тексту, висота за текстом; порожній — «Додати опис»),
    зберігається через `PUT /api/v1/customtables/{id}` з назвою зі змісту й тією самою структурою;
  - назва стовпчика — у самому заголовку (з `UpdateCustomTable`; той самий редагований блок із
    форматуванням, що й текстова клітинка); порожня назва після виходу із заголовка стає «Новий
    стовпчик» (сервер порожньої не прийме); зберігається з таблицею (`PUT` з усіма полями);
  - клітинки — без рамки й підложки, редагований блок із форматуванням виділеного (`appRichText`;
    у значенні лише `b`, `i`, `u`, `s`, `br`, решта очищується, Enter — `<br>`, вставлене — без
    форматування джерела); значення записується як є. Перший символ у порожньому рядку — новий
    запис (ще й з `CreateCustomRecord`, `POST /api/v1/customrecords`; незаповнені поля — порожнім
    рядком), наявні записи — ще й з `UpdateCustomRecord` (`PATCH /api/v1/customrecords/{id}` лише
    зі зміненими тут клітинками: чужі зміни того самого рядка лишаються); рядок має сталий ключ,
    тож курсор не злітає, коли новий запис отримує `id` від сервера;
  - вибір клітинки — натисканням будь-де в ній: у клітинці з текстом (чи порожній) курсор стає в
    поле, у кінець тексту; у клітинці з прапорцем — лише вибір (смуга дій), а перемикає прапорець
    тільки клік по ньому самому (у Safari йому тоді ще й дається фокус);
  - після кожної зміни — 2 секунди тиші (`DebouncedSaver`, `SAVE_DELAY_MS`), тоді всі зміни
    одним збереженням, запити по черзі;
  - тег у шапці: від зміни до відповіді — помаранчевий «Зберігаємо зміни» (`cloud-upload-outline`),
    відмова сервера — червоний «Зміни не збережено» (`cloud-offline-outline`; клік — повторити),
    під час перевірки змін чи перезавантаження записів — синій «Оновлюються дані»
    (`cloud-download-outline`), інакше — зелений «Зміни збережено»;
  - перед пошуком, сортуванням, переходом на іншу таблицю й закриттям виду незбережене
    надсилається одразу; так само, коли вкладку ховають (перемкнули, згорнули, закривають:
    `visibilitychange`), а поки сторінка схована, запити змін ідуть із `keepalive` (`withFetch()` у
    `provideHttpClient`, `writeRequestOptions`) і не обриваються з її закриттям; при закритті
    (`pagehide`) решта черги йде одразу й паралельно; якщо зміни ще не збережено, браузер питає,
    чи залишити сайт (`beforeunload`).

  **Створити шаблон** (кнопка в шапці, з `CreateTableTemplate`): вікно (`app-modal` з
  `app-kb-item-form`) з назвою (спершу — назва таблиці) й описом; «Створити» — `POST
  /api/v1/tabletemplates` зі стовпчиків таблиці: назви заголовків як є (з форматуванням і кольором
  тла) у їхньому порядку; обовʼязковість сервер ще вимагає — усі поля необовʼязкові. Успіх — вікно
  закривається, угорі плашка «Шаблон створено…» (`SuccessNoticeService`); невдача — причина у
  вікні, воно лишається відкритим.

  **Експортувати**: файл Excel `<назва таблиці>.xlsx` (`table-xlsx.ts`) — уся таблиця в поточному
  порядку (незбережене спершу йде на сервер; поки відкрито пошук, записи — заново, без нього), з
  форматуванням, як у застосунку: напівжирний, курсив, підкреслення, закреслення частини тексту,
  колір тла клітинки й заголовка, текст того самого відтінку з контрастом 7:1, переноси рядків
  усередині клітинки (прапорець — `☑` / `☐`). Рядок заголовків — напівжирний і закріплений угорі,
  стовпчики однакової ширини, текст переноситься; усе — текстом, без формул. Файл — zip із XML
  (Office Open XML: книга, аркуш, стилі, спільні рядки), який збирає `storeZip` (`shared/zip`, без
  стиснення, без бібліотек); віддається `downloadFile` (`shared/download`). Не вдалося отримати
  записи — під таблицею «Не вдалося експортувати таблицю.» з причиною й «Спробувати ще раз».

  **Смуга дій** (`app-action-bar` + `ActionBarService`; сторінка «Бази знань» ставить її в
  `ion-content` зі `slot="fixed"` — внизу змісту, не прокручується): поки вибрано клітинку чи
  заголовок. Кнопки лише іконками (назва — у підказці й `aria-label`), натискання не забирає
  курсор із клітинки; недоступне за правами чи для цієї клітинки — вимкнене. Чотири групи,
  рознесені по ширині, між ними — риски (на телефоні, до 600px, — два рядки по дві групи):
  - форматування: кружок кольору тла (див. нижче), напівжирний, курсив, підкреслений, закреслений —
    для виділеного тексту в клітинці чи заголовку, а в клітинці з прапорцем — для всієї клітинки
    (тег навколо символу); у заголовку «Напівжирний» вимкнений: заголовки й так напівжирні;
  - рядки: «Додати рядок знизу» (з `CreateCustomRecord`; курсор — у новий рядок, запис — з
    наступним збереженням; запис створюється між сусідами (`previousRecordId`/`nextRecordId`), тож
    після перезавантаження він на тому самому місці),
    «Видалити рядок» (з `DeleteCustomRecord`, після підтвердження; `DELETE
    /api/v1/customrecords/{id}`);
  - стовпчики: «Додати стовпчик справа», «… зліва» (текстовий «Новий стовпчик»;
    `PUT` таблиці з `id: null` для нового поля; до того в нього тимчасовий `id` (`new:N`), і
    значення його клітинок ідуть на сервер, щойно з `GET` відомий справжній), «Видалити
    стовпчик» (після підтвердження; останній — ні: сервер вимагає хоча б одне поле); з
    `UpdateCustomTable`; дані записів надсилаються лише за наявними полями;
  - клітинка: «Вставити прапорець» (зберігається символом `☑` / `☐`; «так», «+», «1»… стають
    увімкненим; текст, що зник би, — після підтвердження; у клітинці з прапорцем кнопка —
    «Прибрати прапорець»; колір і форматування прапорця лишаються, коли його вмикають чи
    вимикають), «Очистити клітинку», «Скопіювати текст клітинки» (без форматування).

  **Колір тла** всієї клітинки чи заголовка: кружок у смузі дій (кольору нема — пунктирне порожнє
  коло) відкриває вікно (`app-popover` з `app-color-picker`): «Без кольору», 10 пастельних кольорів
  і яскравіший червоний — два рівні ряди по шість, під ними поле HEX тієї самої ширини. Колір
  зберігається в самому значенні клітинки чи назві поля — HTML-тегом навколо всього значення:
  `<div style="background-color: #rrggbb">…</div>` (`splitBackground` / `joinBackground` у
  `shared/rich-text`; старі значення з позначкою `<!--bg:#rrggbb-->` теж читаються): окремого
  місця для стилів клітинок сервер не має. Колір
  тексту не зберігається: `cellTextColor` (`shared/color/cell-colors`) — той самий відтінок, що й
  тло, темніший чи світліший рівно до контрасту 7:1 (де це недосяжно — чорний чи білий, що дає
  більше); у `app-data-table` — `cellColors` і `headerColors` колонки.

  **Перевірка змін** кожні 10 секунд (`POLL_INTERVAL_MS`, поки вкладка видима): таблиця й записи
  (з тим самим пошуком і сортуванням) заново, і показане оновлюється лише там, де щось змінилося
  (`mergeRecords`: незмінені рядки — ті самі обʼєкти, решта клітинок не перемальовується). Поки
  зміни чекають чи йдуть на сервер — перевірка пропускається; відповідь, за час якої щось змінили
  (чи перезавантажили записи), відкидається; рядки з незбереженими змінами, опис під час
  редагування й клітинку з курсором вона не чіпає.

  **Менеджер шаблонів** (`knowledge-base/kb-templates`): заголовок і шаблони з `GET
  /api/v1/tabletemplates`, кожен — візуалізація таблиці, яку з нього буде створено: назва, опис і
  рядок заголовків зі стовпчиків у їхньому порядку (лінії між ними, прокрутка вбік) — з
  форматуванням і кольором тла, як у таблиці. Праворуч від назви — позначка «Системний» (такий
  шаблон сервер не дає ні змінити, ні видалити) чи кнопки-іконки «Редагувати» (`create-outline`, з
  `UpdateTableTemplate`) і «Видалити» (`trash-outline`, з `DeleteTableTemplate`). Створюється
  шаблон у виді таблиці («Створити шаблон»).
  - «Редагувати» — вікно з формою `app-kb-template-form`: назва, опис і «Стовпчики» — рядок
    заголовків, як у таблиці: назву змінюють у самому заголовку (з форматуванням виділеного;
    порожня — «Новий стовпчик»), над ним — вбудована смуга дій для вибраного стовпчика (колір тла,
    курсив, підкреслення, закреслення; «Напівжирного» нема — заголовки й так напівжирні;
    «Додати стовпчик справа», «… зліва» — ключ `column_N`, курсор — у новий; «Видалити стовпчик»,
    останній — ні). «Зберегти» — `PUT /api/v1/tabletemplates/{id}` з усіма стовпчиками (новий — з
    `id: null`; тип і обовʼязковість — текстові, необовʼязкові); видалення стовпчика не
    перепитується: до «Зберегти» нічого не змінено.
  - «Видалити» — підтвердження «Шаблон «…» буде видалено. Таблиці, створені з нього, лишаться.»,
    «Так» — `DELETE /api/v1/tabletemplates/{id}`.
  - Невдача — причина у вікні, воно лишається відкритим; успіх — вікно закривається, список
    оновлюється.

- **Умови до пароля.** Кожна інсталяція налаштовує їх сама (`IdentityOptions` у

  `GET /api/v1/system/identity-options`. `PasswordPolicyService` (`core/auth`)
  питає кожен сервер один раз і віддає умови сигналом: поки відповіді нема чи
  запит не вдався — стандартні (8 символів і всі чотири вимоги), невдалий запит

  «Посібник» зі змістом із таблиць організації, створення, редагування й видалення таблиць, вид
  таблиці з записами (лише перегляд) і менеджер шаблонів (лише перегляд); дій із записами,
  керування шаблонами, виду сторінки, папок, переміщення й загального запиту змісту ще нема (його
  попросили в бекенду); вкладка «Сповіщення» налаштувань,
  кнопка «Зоря» й пункт «Календар» лише намальовані й приховані (`.planned`);
- вкладка «Колеги»: решта даних таблиці замість плейсхолдерів (проєкти; їх сервер
  у списку не віддає), список запрошених, що ще не завершили реєстрацію (в API
  нема запиту), зміст бічного вікна для зміни прав колеги,
  «+» в заголовках таблиці й колонки додаткових полів (право `ViewCustomFields`);
- меню активних токенів для модерування адміністраторами: перелік виданих запрошень і
  посилань скидання пароля (для кого, до коли діє) з можливістю відкликати. API вже є (списки
  запрошень і посилань скидання з видаленням), інтерфейсу ще нема;
- ролі: перевірка прав при створенні й оновленні ролі на сервері (клієнт
  обмежує тумблери, але сервер цього не гарантує);
- використання прав (`permissions`) в інтерфейсі поза пунктом й сторінкою
  «Адмін» і вкладкою «Колеги»: решта меню й сторінок на них поки не реагує;
- «Забули пароль?» на формі входу, у вікні «Додати акаунт» і на формі сторінки
  `/relogin`: посилання поки нічого не робить;
- обмеження пошуку акаунта: кожне відкриття `/login` запускає пошук із запитами до
  серверів усіх акаунтів;
- переклади іншими мовами: усі тексти є лише в `uk.json`, решта мовних файлів
  мають тільки `name`.

## Назви прав

(`core/roles/role-permissions.ts`, назви в `colleagues.roleForm.permissions.*`).

надати групу, користувач має мати всі її коди (AND). Підпункти (з відступом і
лініями `├`/`└`) діють лише разом зі своїм пунктом, як у формі.

## Обмеження, що випливають зі способу постачання

**Статична збірка.** Клієнт — односторінковий застосунок; результат `ng build`
віддає nginx. Образ не містить Node.js. Це знімає потребу в серверному рантаймі
на боці адміністратора інсталяції.

**Порт.** Контейнер слухає порт 8080 (non-root nginx). Локально його
публікує `compose.yaml` на `localhost:8080`; на сервері перед ним стоятиме
зворотний проксі з HTTPS.

**Кешування.** Файли з хешем у назві (`main-*.js`, `chunk-*.js`,
`styles-*.css`, `media/`) кешуються на рік, усе інше, зокрема `index.html`
і `assets/i18n/*.json`, браузер перевіряє щоразу. Тому нові переклади й
зображення в `assets/` підхоплюються без скидання кешу.

**Конфігурація під час виконання.** Один образ працює на всіх інсталяціях, тому
нічого специфічного для середовища не вбудовується у збірку (файлів
`environments/` у проєкті нема). Адресу API клієнт визначає в рантаймі через
`ConnectionService`: адреса сервера активного акаунта (зі збереженого запису)
чи введена користувачем на сторінці входу, а якщо їх нема — домен, з якого
відкрито сторінку (порт 5065 за замовчуванням).

**Без серверної логіки в клієнті.** Автентифікація, валідація та бізнес-правила
реалізовані в `apps/api`. Клієнт не проксує та не агрегує виклики API. Перевірки
у формах (наприклад, складність пароля) виконуються лише для швидкого відгуку
користувачу.

**Токени.** Обидва токени кожного акаунта зберігаються в його записі в
`localStorage`. Це зручно для довільної адреси сервера (куки з іншим сайтом
блокуються), але означає, що XSS у сторінці може прочитати токени.

**Локалізація.** Інтерфейс розрахований на українську, англійську,
кримськотатарську й білоруську мови; мова визначається з мови пристрою при
першому відкритті, а для користувача, який увійшов, — з `preferredLanguage`
його профілю. Тексти зберігаються окремо від компонентів (`assets/i18n/*.json`) з
першого коміту, але поки заповнено лише українські.

## Мобільні застосунки

Ionic дає можливість зібрати клієнт як мобільний застосунок через Capacitor.
Пакети `@capacitor/*` уже є в `package.json` (частина шаблону), але
`capacitor.config` і нативні проєкти відсутні. Рішення про мобільний застосунок
не ухвалене. Наслідок для архітектури: мобільний застосунок стає другим
споживачем API з власним циклом випуску, що вимагає політики сумісності API,
якої зараз немає.

## Використання ШІ

Під час написання активно використовувалися інструменти ШІ, однак усі технічні
рішення (архітектура, алгоритми, бізнес-правила, права доступу) та логіка UX
зроблені людиною. Весь код регулярно вичитується та перевіряється вручну.
