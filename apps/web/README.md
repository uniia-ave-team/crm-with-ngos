# Вебклієнт

Клієнт на Ionic Angular. Каталог самодостатній: `package.json` і
`package-lock.json` розташовуються тут, а не в корені репозиторію. Спільного
workspace з `apps/api` немає. Пакет називається `Yavir`.

Застосунок має робочу оболонку (бокове меню, шість сторінок, локалізація) і
сторінку входу, яка вже працює з `apps/api`: перевіряє підключення, веде через
первинне налаштування системи (адміністратор, організація), виконує вхід і
підтримує сесію. Сесія — це збережені в `localStorage` акаунти (див.
«Акаунти»), але **користувач поки може мати лише один акаунт**: способу додати
другий нема. Решта сторінок поки порожні заглушки без вмісту.

## Стек

| Частина          | Версія / інструмент                                              |
|------------------|------------------------------------------------------------------|
| Фреймворк        | Angular 22, NgModule-архітектура (не standalone)                 |
| UI               | Ionic Framework 9 (`@ionic/angular/lazy`), Ionicons 8            |
| Локалізація      | `@ngx-translate/core` 18 (standalone API, без `TranslateModule`) |
| Шрифт            | e-Ukraine (Regular/Light/Medium/Bold), локально в `assets/fonts` |
| Мова             | TypeScript 6                                                     |
| Збірка           | Angular CLI 22, builder `@angular/build:application`             |
| Тести            | Vitest 4 + jsdom через `ng test`                                 |
| Лінтер           | ESLint 10, angular-eslint, typescript-eslint                     |
| Менеджер пакетів | npm                                                              |

## Вимоги

Node.js **22.22.3 або новіший** (також підходять 24.15+ і 26+).

## Команди

Усі команди виконуються в `apps/web`.

```bash
npm install                        # встановити залежності
npm start                          # ng serve, http://localhost:4200
npm run build                      # production-збірка у www/
npm run watch                      # збірка з перезбиранням (development)
npm test                           # Vitest у режимі спостереження
npm run test:ci                    # Vitest, один прогін (для CI)
npm run lint                       # ESLint для src/**/*.ts і src/**/*.html
npm run lint:fix                   # ESLint з автовиправленням
npm run generate:api               # клієнт API з openapi.json
```

З кореня репозиторію те саме доступне через `just`: `just web`,
`just test-web`, `just web-ci`.

`npm start`, `npm run build` і тести спершу генерують клієнт API з
`packages/api-contract/openapi.json` у `src/app/api/generated` (каталог
ігнорується git).

`ng build` кладе результат у `www/`, а не в `dist/`. Саме звідти `Dockerfile`
копіює статику для nginx. Каталог `www/` ігнорується git.

Production-образ локально: `just up` з кореня репозиторію, потім
<http://localhost:8080>. API, яке піднімає `just up`, слухає
`http://localhost:5065` і приймає запити й з `ng serve` (`:4200`), тож для
роботи з реальними даними .NET не потрібен: `just up`, потім `npm start`.

Бюджети production-збірки: початковий бандл — попередження від 2 МБ, помилка
від 5 МБ; стилі компонента — 4 і 8 КБ.

## Поточний стан

Створено:

- **Каркас і навігація.** `AppComponent` — оболонка застосунку: бокова панель
  (`core/layout/primary-nav`, десктопна колонка / мобільні верхня й нижня
  панелі) і друга контекстна панель (`core/layout/secondary-panel`) для
  сторінок «База знань» і «Планер». Сторінки без бічного меню взагалі
  (наразі — лише `/login`) позначаються `data: { layout: 'none' }` у
  маршруті й читаються через `LayoutService.hideShell`; місце під мобільні
  панелі резервується лише всередині оболонки. Поки йде пошук чинного
  акаунта (старт застосунку, перехід на захищену сторінку), поверх усього
  показується повноекранний прелоадер (`shared/preloader`).
- **Шість сторінок:** `calendar`, `planner`, `knowledge-base`, `colleagues`,
  `settings` (порожні заглушки з перекладеним заголовком) і `login` — єдина
  сторінка з реальним вмістом, без бічного меню. На стартовій адресі `/`
  відбувається переадресація на `/login`.
- **Сторінка входу** веде користувача через підключення, первинне
  налаштування системи й вхід. Якщо в `localStorage` є збережені акаунти,
  спершу шукається чинний (див. «Акаунти»): знайшовся — одразу перехід на
  `REDIRECT_URL` (зараз `/planner`), форми не показуються, а поки пошук
  триває, видно «Перевіряємо підключення…». Якщо акаунтів нема або жоден не
  чинний, перевіряється підключення: немає — форма адреси сервера; є —
  запитується `GET /api/v1/system/status`. Далі за статусом і наявністю
  активного акаунта (він з'являється, коли користувач щойно ввійшов або
  зареєстрував адміністратора на цій сторінці). Рядки перевіряються зверху
  вниз; `—` означає «неважливо»:

  | `isSetupComplete` | `hasAdmin` | `hasNgo` | Активний акаунт | Результат                       |
  |-------------------|------------|----------|-----------------|---------------------------------|
  | `true`            | —          | —        | немає           | форма входу                     |
  | `true`            | —          | —        | є               | перехід на `REDIRECT_URL`       |
  | `false`           | `false`    | —        | —               | форма реєстрації адміністратора |
  | `false`           | `true`     | `false`  | є               | форма створення ГО              |
  | `false`           | `true`     | `false`  | немає           | форма входу                     |
  | `false`           | `true`     | `true`   | —               | помилка налаштування системи    |

  Якщо статус отримати не вдалося, показується форма входу. Помилка
  налаштування системи має текст «Сталася помилка при налаштуванні системи.»

  - **Форма входу** (зображення зліва, форма справа; на вузьких екранах лише
    форма): пошта й пароль. `POST /api/v1/auth/login`, вхід зберігається
    як акаунт (адреса сервера, токени, пошта), запитується статус системи: немає ГО — форма створення ГО, є — перехід
    на `REDIRECT_URL`. Лого Явору — мобільне лого меню (за мовою й темою),
    лого Унії — `Uniia.svg` для української, кримськотатарської й білоруської,
    `Uniia_en.svg` для решти; лого партнерів і зображення — зі світлими
    (`assets/logos`) і білими (`assets/logos_white`) варіантами для темної
    теми.
  - **Форма адміністратора:** пошта, прізвище, імʼя, пароль і його повтор;
    `POST /api/v1/users`, потім одразу `POST /api/v1/auth/login` з тими самими
    даними. Пароль має відповідати правилам сервера (`IdentityOptions` в
    налаштуваннях API): від 8 символів, велика й мала латинські літери,
    цифра та спецсимвол; умови виведено списком під полем пароля й
    відмічаються під час введення, під повтором відмічається збіг паролів.
  - **Форма ГО:** назва й логотип (поле перетягування з превʼю та круглою
    кнопкою видалення); `POST /api/v1/ngo`, потім перехід на `REDIRECT_URL`.
  - **Кнопка «змінити адресу сервера»** (кругла, з іконкою сервера, праворуч
    угорі кожної форми, крім кроку адреси): спершу один запит `GET /health`
    на поточний сервер, потім повне очищення `localStorage` і форм та
    повернення на крок адреси; якщо сервер був здоровий, його адресу
    підставлено в поле. Кнопка скидає все, що збережено в браузері для
    застосунку: адресу сервера, мову, акаунт, який зараз налаштовується
    (наприклад, щойно створеного адміністратора, коли відкрито форму ГО), і
    застарілі акаунти. Інших акаунтів на цій сторінці бути не може: чинний
    акаунт перекинув би користувача на `REDIRECT_URL`.
  - **Помилки:** валідація форм — до будь-якого запиту. Помилки полів
    показуються під ними, а відповіді сервера (і помилка прізвища у формі
    адміністратора) — окремим блоком над формою.
  - Усім полям і кнопкам задано `tabindex`, бо в Safari без нього не працює
    табуляція.
- **`ConnectionService`** (`core/connection`) — визначає, до якого сервера
  підключатися, і перевіряє його:
  - адреса сервера: надана користувачем (зберігається в памʼяті, а після
    входу — у записі акаунта) має пріоритет і без запасного варіанта; якщо її
    нема — домен, з якого відкрито сторінку. Порт за замовчуванням — 5065;
  - перевірка `GET <сервер>/health` (таймаут 5 с) дає стан `healthy`,
    `unhealthy` або `unreachable`; результат виводиться в консоль;
  - `loadSystemStatus()` запитує `GET <сервер>/api/v1/system/status`.
- **Стражі сторінок** (`core/auth`, `core/connection`). Усі сторінки, крім
  `/login`, проходять `authGuard`, а потім `connectionGuard`. `authGuard`
  шукає чинний акаунт серед збережених так само, як сторінка входу, і перший
  знайдений стає поточним. Результат пошуку: `restored` — пускає; `none` —
  переадресація на `/login`; `unavailable` — чинного нема, і причиною був хоч
  один акаунт, чий сервер не відповів, — переадресація на
  `/login?error=no-connection`. Це **тимчасове рішення**: інтерфейсу
  додавання акаунтів поки нема, тож `/login` — єдине місце, де можна ввійти;
  коли він з'явиться, а в застосунку лишаться інші акаунти, поведінку треба
  переглянути. Якщо поточний акаунт уже підтверджено в цій сесії сторінки,
  пошук пропускається. `connectionGuard` додатково вимагає, щоб API за
  поточною адресою відповідав, інакше теж `/login?error=no-connection`.
- **Акаунти** (`core/accounts`):
  - `AccountsService` — сховище акаунтів у `localStorage`: запис на акаунт
    (`yavir.account.<id>`), індекс (`yavir.accounts`) і вказівник на активний
    (`yavir.activeAccount`). Запис містить адресу сервера, токени, пошту,
    ознаку користувача (`identity`), знімок профілю (імʼя, прізвище, аватар,
    назва та посилання на логотип ГО), прапорці `outdated` і `unavailable`
    та час отримання токенів (`tokensIssuedAt`). `id` акаунта —
    домен сервера лише латинськими літерами та хеш сервера й користувача
    (наприклад, `localhost-3ee638bc`); при збігу хешу додається суфікс `-2`,
    `-3`. Зміни в інших вкладках підхоплюються через подію `storage`;
  - `AccountRestoreService` — пошук чинного акаунта: проходить акаунти
    (активний першим) і для кожного перевіряє `/health`, за потреби оновлює
    токени й підтверджує вхід запитом `GET /users/me`. Перший чинний стає
    активним. Акаунт, чиї токени сервер відхилив або чий сервер не
    відповідає, не видаляється, а позначається `outdated` (для недоступного
    сервера додатково `unavailable`) і більше не перевіряється; якщо він був
    активним, активним стає перший чинний. Якщо чинних не лишилося, сховище
    очищається повністю (тимчасово, див. «Ще не зроблено»).
- **Сесія й токени** (`core/auth`):
  - `AuthService` — вхід та токени активного акаунта (access і refresh лежать
    у його записі); обмін токенів (`POST /api/v1/auth/refresh-token`)
    потребує обох. Refresh-токен одноразовий, тому обмін іде в одному
    екземплярі: у межах вкладки — один спільний запит, між вкладками — Web
    Lock; нову пару, записану іншою вкладкою, підхоплюють зі сховища (подія
    `storage`), а не стирають. Невдале оновлення (400/401) позначає акаунт
    застарілим;
  - `authInterceptor` — додає `Authorization: Bearer <accessToken>` до
    запитів до `/api/...` (крім входу, оновлення токенів, статусу системи й
    `POST /users`); прострочений за `exp` токен оновлює до запиту, а на 401
    оновлює токени й повторює запит один раз. Якщо оновити токени не вдалося —
    вихід: акаунт забуто, перехід на `/login`;
  - `SessionService` — у фоні оновлює токени перед завершенням терміну
    access-токена (також коли вкладка знову стає видимою). Окремо оновлює
    токени **неактивних** акаунтів, у яких минула половина терміну
    refresh-токена: після завершення пошуку акаунта, при поверненні вкладки у
    фокус і раз на годину. Термін refresh-токена клієнт не знає (сервер його не
    віддає), тому припускає 7 днів, як у налаштуваннях API за замовчуванням.
    Відхилені токени позначають акаунт застарілим, мережева помилка нічого не
    змінює. Якщо токени зникли, а ми не на `/login`, переносить на `/login`
    (під час пошуку акаунта ця перевірка мовчить);
  - `CurrentUserService` (`core/users`) — `GET /users/me`: підтверджує вхід і
    дає профіль для меню, а також записує знімок профілю, назву й посилання на
    логотип ГО в запис акаунта;
  - `UsersService` (`core/users`) — створення користувача;
  - `NgoService` (`core/ngo`) — створення організації (`logoUrl` завжди
    `null`) і читання її назви та посилання на логотип.
- **«Вийти» поки працює не так, як задумано.** Кнопка не видаляє поточний
  акаунт, а очищає весь `localStorage` (усі акаунти, мову, стан панелі),
  переносить на `/login` і лише потім відкликає refresh-токен активного
  акаунта запитом `POST /api/v1/auth/logout`. Тобто вихід з одного акаунта
  виходить з усіх. Логіку не змінено: заплановано видаляти лише активний
  акаунт і переходити на наступний.
- **Акаунти додаються лише через `/login`, і лише перший.** Поки є чинний
  акаунт, `/login` перекидає на `REDIRECT_URL`, тож додати другий неможливо.
  Для цього планується окремий елемент інтерфейсу.
- **Меню акаунта.** Аватар у бічній панелі відкриває спливаюче вікно
  (`shared/popover`), а в ньому `core/layout/account-menu`: список акаунтів,
  кнопка додавання, «Налаштування профілю» й «Вийти». Колір аватара без
  зображення рахується з імені, прізвища й назви ГО (`shared/avatar`, алгоритм
  у `avatar-color.ts`, контраст ≥ 4.5:1 і з білим, і з чорним). Список
  акаунтів береться зі збережених у `localStorage` (знімок профілю й ГО в
  записі акаунта, без запитів), у порядку додавання; активний має білу
  рамку, застарілий — сірий аватар і значок ліворуч унизу: жовтий
  `sync-circle` (токени відхилено) або червоний `alert-circle` (сервер не
  відповів).
  Значок логотипа ГО праворуч унизу з'являється лише за наявності
  `ngoLogoUrl` (немає — плитка без значка). Клік по плитці й кнопка
  додавання лише закривають вікно. «Налаштування профілю» веде на
  `/settings`.
- **Спільні компоненти** (`shared/`): `avatar`; `popover` (універсальне
  спливаюче вікно, прив'язане до елемента; закривається клацанням поза ним і
  клавішею Esc, `close()` повертає проміс, що виконується після завершення
  анімації закриття); `preloader`; директива `alpha-outline` (контур за
  альфа-каналом зображення).
- **Локалізація.** `@ngx-translate/core` 18 (сучасний standalone API, без
  `TranslateModule` — `provideTranslateService`/`provideTranslateHttpLoader`
  і стандалонний `TranslatePipe`). Чотири мови — українська, англійська,
  кримськотатарська, білоруська (`src/assets/i18n/*.json`). Мова
  визначається автоматично з мови пристрою при першому відкритті
  (`LanguageService`, `core/i18n`), зберігається в `localStorage` й
  синхронізується між вкладками. Запасна мова для всіх — українська.
  **Заповнений лише `uk.json`.** Файли `en.json`, `crh.json` і `be.json`
  повністю очищено (в кожному лише `{}`), і вони лишаться порожніми, доки не
  зʼявиться фінальний переклад. Тож у будь-якій мові інтерфейс зараз
  показується українською через запасну мову. Переклади, які були там раніше,
  були тимчасовими плейсхолдерами.
- **Шрифт e-Ukraine** — чотири ваги (Regular, Light, Medium, Bold),
  `assets/fonts/*.otf`, ліцензія CC BY 4.0 (джерело — дзеркало офіційного
  шрифту Мінцифри, `assets/fonts/LICENSE.txt`).
- **Лого.** Мобільне лого — окремі SVG для кожної мови
  (`assets/logo_mobile_*.svg`, вибір за мовою в `core/i18n/mobile-logo.ts`);
  лого Унії та партнерів — `assets/logos` і `assets/logos_white`.
- Кольорові токени світлої/темної теми та `ion-toolbar` (`src/theme/`).
- `environment.ts` / `environment.prod.ts` з єдиним прапорцем `production`.
- Клієнт API, згенерований з `openapi.json` (`src/app/api/generated`), поки
  ніде не використовується: запити сторінки входу йдуть через `HttpClient`.
- `proxy.conf.json`: `ng serve` перенаправляє `/api` на API за адресою
  `http://localhost:5065`.

Ще не зроблено:

- UI самих сторінок — `calendar`, `planner`, `knowledge-base`, `colleagues`
  і `settings` поки порожні заглушки;
- завантаження логотипа ГО на сервер: файл лише обирається й показується в
  превʼю, а API приймає логотип тільки як URL (у запиті `logoUrl` завжди
  `null`);
- підвантаження бокових зображень у формі входу: зображення зараз лежить у
  збірці (`assets/login_image.jpg`) і не береться з API;
- «Забули пароль?» на формі входу: посилання поки нічого не робить;
- додавання акаунтів: окрім першого через `/login` способу нема, для цього
  планується окремий елемент інтерфейсу (кнопка додавання в меню акаунта поки
  лише закриває вікно);
- перемикання між акаунтами: клік по плитці в меню акаунта лише закриває меню;
- правильна логіка «Вийти»: видалення лише активного акаунта замість повного
  очищення `localStorage` (див. вище);
- відновлення недійсних акаунтів замість тимчасового `wipe` (єдиний
  механізм). Зараз акаунт, чиї токени відхилено або чий сервер не відповів,
  позначається `outdated` (з `unavailable`, якщо сервер не відповів), а коли
  чинних не лишилося, сховище очищається повністю, як при виході. Через це
  один розрив мережі під час старту викидає з усіх акаунтів, а вибрати в меню
  застарілий чи недоступний акаунт неможливо: клік по плитці лише закриває
  меню. Потрібно замінити `wipe` і додати: 1) повторну спробу підключення для
  недоступного акаунта без видалення його токенів; 2) перезахід для
  застарілого й недоступного акаунта, який користувач вибирає в меню акаунтів
  (форма входу з уже відомою адресою сервера й поштою, після успіху акаунт
  знову стає чинним);
- переклад вмісту сторінок: лише меню, заголовки й сторінка входу (і та
  лише українською);
- перемикач мови в інтерфейсі (наразі тільки автовизначення).

## Обмеження, що випливають зі способу постачання

**Статична збірка.** Клієнт — односторінковий застосунок; результат `ng build`
віддає nginx. Образ не містить Node.js. Це знімає потребу в серверному рантаймі
на боці адміністратора інсталяції.

**Порт.** Контейнер слухає порт 8080 (non-root nginx). Локально його
публікує `compose.yaml` на `localhost:8080`; на сервері перед ним стоятиме
зворотний проксі з HTTPS.

**Кешування.** Файли з хешем у назві (`main-*.js`, `chunk-*.js`,
`styles-*.css`, `media/`) кешуються на рік, усе інше, зокрема `index.html`
і `assets/i18n/*.json`, браузер перевіряє щоразу. Тому нові переклади й
зображення в `assets/` підхоплюються без скидання кешу.

**Конфігурація під час виконання.** Один образ працює на всіх інсталяціях, тому
нічого специфічного для середовища не вбудовується у збірку, зокрема в
`environments/`. Адресу API клієнт визначає в рантаймі через
`ConnectionService`: надана користувачем адреса з `localStorage` або домен, з
якого відкрито сторінку (порт 5065 за замовчуванням). Під час розробки `ng
serve` додатково проксує `/api` на `http://localhost:5065`.

**Без серверної логіки в клієнті.** Автентифікація, валідація та бізнес-правила
реалізовані в `apps/api`. Клієнт не проксує та не агрегує виклики API. Перевірки
у формах (наприклад, складність пароля) виконуються лише для швидкого відгуку
користувачу.

**Токени.** Обидва токени кожного акаунта зберігаються в його записі в
`localStorage`. Це зручно для довільної адреси сервера (куки з іншим сайтом
блокуються), але означає, що XSS у сторінці може прочитати токени.

**Локалізація.** Інтерфейс розрахований на українську, англійську,
кримськотатарську й білоруську мови; мова визначається автоматично з мови
пристрою при першому відкритті. Тексти зберігаються окремо від компонентів
(`assets/i18n/*.json`) з першого коміту, але поки заповнено лише українські.

## Мобільні застосунки

Ionic дає можливість зібрати клієнт як мобільний застосунок через Capacitor.
Пакети `@capacitor/*` уже є в `package.json` (частина шаблону), але
`capacitor.config` і нативні проєкти відсутні. Рішення про мобільний застосунок
не ухвалене. Наслідок для архітектури: мобільний застосунок стає другим
споживачем API з власним циклом випуску, що вимагає політики сумісності API,
якої зараз немає.
